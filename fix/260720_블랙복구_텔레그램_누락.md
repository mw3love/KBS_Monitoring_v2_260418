## 2. 체계적으로 배제한 것 (로그 근거)

발송 실패였다면 반드시 로그가 남는다(모든 실패 경로가 `_log_with_suppression`로 최소 info라도 기록). 그런데:

| 가설 | 판정 | 근거 |
|---|---|---|
| 전송 실패/네트워크/429 | ✗ | 실패·재시도·Rate Limit 로그 0건 |
| 큐 가득참 드롭 | ✗ | `queue.Queue(maxsize=50)`, "손실" 로그 0건 |
| 정파 억제 | ✗ | 7/19 정파는 2TV뿐, 모악(V3·V7) 정파 이력 없음 |
| Detection 재spawn 상태 리셋 | ✗ | 7/19 detection 연속 가동(threads=8, 재기동 0) |
| 알림 비활성/`블랙` 플래그 off | ✗ | 같은 플래그로 진입 알림은 나감 |

→ 남는 결론: **복구 분기(`processes/detection_process.py` `_process_alarms`의 `elif not alerting and was:`)가 발화하지 않았거나, `telegram.notify(is_recovery=True)`가 큐에 안 들어감.** 텔레그램 전송 계층 문제 아님.

## 3. 왜 로그만으로 더 못 파는가 (구조적 계측 공백)

`AlarmResolve`(블랙 해제)와 복구-알림 분기 판정이 **어느 로그 파일에도 안 남는다**:
- UI `main_window._on_alarm_resolve` → 화면 로그 위젯에만 "복구" 기록, **파일 미기록**(진입 "감지" 줄도 파일에 없음).
- Detection `_process_alarms` 복구 분기 → `LogEntry` 미발행. 텔레그램 "복구 전송 완료" 한 줄만이 파일에 남는 유일한 복구 흔적.

→ 그 한 줄이 없으면 "블랙이 안 풀림"과 "풀렸는데 알림 누락"을 **파일로 구분 불가**. (이번엔 사용자 육안으로 후자 확정.)

## 4. 진단 로깅 (2026-07-20 심음 · 로직 무변경)

추측 수정은 원인 미확정 상태에서 새 실패 모드를 넣을 위험. **먼저 계측을 심고 다음 재발을 관측**한다. `processes/detection_process.py` `_process_alarms`에 `LogEntry`만 추가(동작 무변경, `grep DIAG-복구추적`):

- **진입** (비디오 블랙/스틸): `DIAG-복구추적 {lbl} {det_type} 감지 (suppressed=…)`
- **해제** (비디오 블랙/스틸 + 오디오 + EA): `DIAG-복구추적 {lbl} {det_type} 해제 → {갈래}` — 갈래 = `복구문자 발송` / `억제(정파 SIGNOFF)` / `억제(정파 해제 2차)`.
- 이 로그들은 `result_queue`→UI 로그 파일(`logs/YYYYMMDD_ui.txt`)에 남는다.

**다음 재발 시 판독법** (블랙이 실제 복구된 것이 육안 확인된 상태에서):

```
"해제 → 복구문자 발송" 있는데 텔레그램 안 옴   → 발송단 문제 (telegram_worker)
"해제 → 억제(…)"                              → 억제 로직 오발동
"감지"만 있고 "해제" 줄이 아예 없음           → 복구 분기 미발화
                                               = detector가 alerting=False 전이를 못 봄
                                                 (히스테리시스/프레임공급) → 다음 단계는
                                                 alerting 상태 heartbeat 로그 추가
```

⚠ **임시 계측이다.** 원인 특정 후 `DIAG-복구추적` 줄은 제거(또는 config 플래그로 강등). 상시 로그로 굳히지 말 것.

## 5. 유력 가설 (미검증)

- **7/18 8채널 케이스**: 8개 복구 아이템이 동시에 워커 큐에 들어갔고, 워커가 V1~V4 sendPhoto 후(각 4~7초, 텔레그램 미디어 속도제한 정황) **V5부터 조용히 멈춤** — 에러 로그 없이. 워커 스레드/큐 상태 이상 의심. 단 워커 루프는 `_send` 예외를 try/except로 잡으므로 "조용한 중단" 경로가 무엇인지는 §4 로깅으로 확인 필요.
- **7/19 단일 V7**: 위와 달리 캡처상실 없음 → 워커 폭주 가설과 무관. 복구 분기 자체 미발화 가능성이 더 큼. **두 케이스가 다른 원인일 수 있다** — 로깅으로 분리 확인.

→ §5 두 가설 모두 틀렸다. 두 케이스는 같은 원인이다(§6).
