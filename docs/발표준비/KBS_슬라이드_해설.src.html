KBS 발표 슬라이드 해설

발표 덱 13장(본편 10장 + 부록 3장)을 한 장씩 풀어 쓴 공부용 문서. 슬라이드에 나온 낱말의 뜻, 그 뒤에 있는 원리, 심사위원이 물을 만한 것, 그리고 쉽게 바꾼다면 무엇을 뺄지까지 적었다.

읽는 법
  • 장마다 같은 순서다: 슬라이드 그림 → 한 줄 요지 → 이 장이 말하는 것 → 낱말 풀이 → 비유 → 나올 만한 질문 → 쉽게 만든다면.
  • 「쉽게 만든다면」은 제안일 뿐 아직 덱에 반영하지 않았다. 읽고 나서 어느 장을 얼마나 쉽게 할지 정하면 그대로 고친다.
  • 회색 글씨 「추정:」은 코드나 문서로 확인하지 못한 설명이다. 발표에서 단정하지 말 것.
  • 어려움 ★은 「기술 비전공자가 처음 읽을 때」 기준이다. ★★★이 가장 어렵다.

01

표지 — v1에서 v2로

어려움 ★★☆약 50초

옛 버전(v1)은 프로그램 하나가 모든 일을 해서, 오래 켜 두면 감시가 멈췄다. 새 버전(v2)은 프로그램을 셋으로 나누고, Watchdog이 나머지 둘이 살아 있는지 확인하게 했다.

이 장이 말하는 것

KBS Monitoring은 방송 16채널을 사람 대신 지켜보다가, 화면이 까맣게 되거나(블랙) 멈추거나(스틸) 소리가 끊기면 경보를 울리고 텔레그램으로 알려 주는 프로그램이다. 판정은 AI 학습이 아니라 사람이 정한 숫자 기준(예: 밝기 5 미만)으로 한다. 이것을 「규칙 기반」이라고 부른다.

v1(옛 이름 KBS Peacock 1.6)은 화면 그리기와 감시를 한 프로그램 안에서 했다. 그런데 며칠씩 켜 두면 감시하는 반복 작업이 조용히 멈추는 일(freeze)이 생겼다. 원인을 하나로 찾기 어려웠기 때문에, v2는 「원인이 무엇이든 멈추면 다른 쪽이 알아채고 되살리는 구조」로 다시 만들었다(2026-04-18 시작).

표의 세 줄이 그 차이를 요약한다.

  • 구조: 한 프로그램 → 세 프로그램(UI·Detection·Watchdog).
  • 장기 운영: 멈추면 끝 → heartbeat(생존 신호)로 멈춤을 알아채고 자동으로 다시 띄움.
  • 장애 통보: 고장 난 쪽이 직접 알림(고장 났으니 못 보낼 수 있음) → 멀쩡한 쪽이 대신 알림.

낱말 풀이

프로세스 (process)
컴퓨터에서 따로따로 돌아가는 프로그램 하나. 저마다 자기 메모리를 쓴다. 그래서 하나가 망가져도 다른 프로세스에는 번지지 않는다.
스레드 (thread)
한 프로세스 안에서 동시에 일하는 일꾼. 같은 메모리를 함께 쓴다. 그래서 일꾼 하나가 꼬이면 프로세스 전체가 같이 꼬일 수 있다. v1의 「감지 스레드」가 이 경우.
UI
User Interface. 사람이 보는 화면과 버튼.
Detection
실제로 영상·소리를 검사하는 프로세스.
Watchdog
「감시견」. Detection이 살아 있는지 지켜보다가 죽으면 다시 띄우는 프로세스.
감지 루프 freeze
0.2초마다 도는 검사 반복이 멈춘 상태. 창은 멀쩡히 떠 있어서 사람은 모른다. 이게 가장 위험하다.
heartbeat
「심장 박동」. 프로그램이 주기적으로 파일에 지금 시각을 적어 「나 살아 있어」를 알리는 것.
재spawn
spawn은 새 프로세스를 띄우는 것. 재spawn은 죽은 프로세스를 새로 다시 띄우는 것.
OpenCV
영상 처리용 무료 공개(오픈소스) 도구 모음. 화면을 숫자 배열로 다룬다.
비유: v1은 혼자 야간 근무하는 감시원이다. 졸아도 아무도 모른다. v2는 세 사람이다. 모니터를 보는 감시원(Detection), 상황판을 관리하는 사람(UI), 그리고 10초마다 감시원이 깨어 있는지 확인하는 반장(Watchdog). 감시원이 졸면 반장이 바로 교대시키고, 상황실에 직접 연락한다.

나올 만한 질문

Q. freeze 원인을 고치지 않고 왜 구조를 바꿨나?

원인이 하나로 특정되지 않았다. 며칠 운영해야 나타나서 재현도 어려웠다. 그래서 「어떤 이유로 멈추든 알아채고 되살린다」를 목표로 잡았다. 실제로 v2 운영 중 원인이 다른 장애(캡처보드, 시계 점프, 힙손상)가 여러 번 있었는데, 구조 덕분에 감시는 계속됐다.

Q. AI(딥러닝)를 쓰지 않은 이유는?

찾는 사고가 블랙·정지·무음처럼 숫자로 분명히 정의되는 것들이다. 규칙 기반은 왜 경보가 났는지 설명할 수 있고, 학습 데이터나 GPU가 필요 없다. 추정: 심사에서 이 질문이 나오면 「설명 가능성」과 「기존 PC로 충분」 두 가지로 답하면 된다.

쉽게 만든다면
  • 표의 「단일 프로세스 (UI + 감지 스레드)」 → 「프로그램 하나가 화면과 감시를 같이 처리」.
  • 「heartbeat 감시 → 자동 재spawn」 → 「살아 있는지 10초마다 확인, 멈추면 자동 재시작」.
  • 부제의 「3-프로세스 격리」는 그대로 두고, 말로 「셋으로 나눴다」를 덧붙인다.
02

시스템 구성 — 멀티뷰어 한 화면이 입력

어려움 ★★☆약 1분

채널마다 장비를 따로 붙이지 않는다. 16채널이 다 나오는 멀티뷰어 화면 한 장을 PC로 받아, 그 위에 사각형(감지영역)을 그려 센서처럼 쓴다.

이 장이 말하는 것

신호는 왼쪽에서 오른쪽으로 흐른다.

  1. 방송 신호(1TV·2TV·UHD 등)가 SDI 케이블로 들어온다.
  2. 멀티뷰어가 16채널을 바둑판처럼 한 화면에 모으고, 채널 옆에 소리 크기 막대(레벨미터)도 그려 준다.
  3. 캡처보드가 그 화면(1920×1080)과 소리를 PC가 읽을 수 있는 데이터로 바꾼다.
  4. 감시PC의 KBS Monitoring이 0.2초마다 검사한다.
  5. 이상하면 화면 경보·경보음, 텔레그램 알림, 사고 앞뒤 MP4 녹화를 남긴다.

왼쪽 아래 그림은 실제 운영 화면 확대다. 빨간 사각형 V1은 1TV ON-AIR 영상을 보는 감지영역, 레벨미터 위 주황 사각형 A1은 같은 채널의 소리 막대를 보는 감지영역이다.

핵심 발상은 마지막 문장이다. 보통은 채널마다 디코더(신호를 영상으로 푸는 장비)와 디임베더(신호 속 소리를 꺼내는 장비)를 둬야 하는데, 이미 있는 멀티뷰어 출력을 그대로 쓰니 장비가 하나도 늘지 않는다.

낱말 풀이

SDI
방송국에서 쓰는 표준 디지털 영상 신호(케이블). 영상과 소리가 한 선에 같이 들어간다.
멀티뷰어
여러 채널을 한 모니터에 나눠 보여 주는 장비.
캡처보드
영상 신호를 PC로 받아들이는 장치. PC 입장에서는 웹캠처럼 보인다.
임베디드 오디오
SDI 영상 신호 안에 섞여(embedded) 들어가는 소리.
감지영역 (ROI)
Region of Interest. 화면에서 검사할 부분만 사각형으로 지정한 것. V는 영상, A는 레벨미터, EA는 임베디드 오디오.
cv2.VideoCapture(port, CAP_DSHOW)
OpenCV로 캡처 장치를 여는 명령. CAP_DSHOW는 윈도우의 DirectShow라는 방식으로 연다는 뜻.
BUFFERSIZE=1
장치가 쌓아 두는 화면을 1장으로 제한. 여러 장 쌓이면 몇 초 전 화면을 검사하게 되어 늦게 알아챈다. 1장이면 늘 가장 최신 화면.
sounddevice · int16 PCM
sounddevice는 파이썬에서 소리 입력을 받는 도구. PCM은 압축하지 않은 소리 데이터, int16은 그 값을 −32768~32767 정수로 나타낸다는 뜻.
판정 주기 200 ms
0.2초마다 한 번 검사. 1초에 5번. 설정에서 0.1·0.2·0.5·1초 중 고를 수 있다.
스택
사용한 도구 묶음. PySide6(화면), OpenCV(영상), NumPy(숫자 계산), sounddevice(소리), ffmpeg(영상 파일 만들기), psutil(프로세스 상태 조회), requests(인터넷 요청 — 텔레그램 발송).
Telegram Bot API
텔레그램 봇이 메시지를 보내는 인터넷 창구. 주소로 요청을 보내면 메시지가 간다.
비유: CCTV 16대마다 경보기를 다는 대신, 관제실 모니터 벽을 카메라 한 대로 찍어 두고 화면의 칸마다 「여기를 봐」 스티커를 붙인 것. 스티커 하나하나가 센서다.

나올 만한 질문

Q. 멀티뷰어 화면은 축소된 영상인데 정확도가 괜찮나?

찾는 사고가 블랙·정지·무음처럼 화면 전체에 드러나는 큰 사고라 축소에 강하다. 반대로 미세한 화질 열화(블록 노이즈 등)는 이 방식의 대상이 아니다. 한계로 인정하면 된다.

Q. 멀티뷰어나 캡처보드가 고장 나면?

캡처 신호가 끊기면 화면 전체가 「검정 + 직전과 똑같은 프레임」이 된다. 이를 따로 알아채 캡처 장치만 다시 연다(8장 ①). 추정: 멀티뷰어 출력이 멈춰 그림이 얼어붙으면 모든 채널이 스틸로 잡혀 경보가 날 것이다. 실제로 겪은 기록은 확인 못 함.

Q. 왜 디임베더 대신 레벨미터 그림을 읽나?

캡처보드로 들어오는 실제 소리는 1조(L/R)뿐이다. 나머지 채널의 소리 유무는 멀티뷰어가 그려 주는 미터를 영상으로 읽어서 판단한다(5장).

쉽게 만든다면
  • 오른쪽 표를 「입력: 1920×1080 화면 + 소리」, 「감지영역: 영상 8 · 레벨미터 6 · 소리 1」, 「검사: 1초에 5번」 3줄로 줄인다.
  • cv2.VideoCapture, BUFFERSIZE, int16 같은 코드 이름은 발표 메모로 옮긴다(질문 나오면 답).

처리 파이프라인 — 0.2초 한 바퀴

어려움 ★★★약 1분

감시 프로그램(Detection) 안에서 여러 일꾼이 나눠 일한다. 느린 일(인터넷 발송, 영상 파일 만들기)은 따로 빼서, 검사는 늘 0.2초 박자를 지킨다.

이 장이 말하는 것

윗줄 — 캡처 일꾼. 캡처보드에서 최신 화면을 계속 읽어(cap.read()) 공유 메모리에 쓴다. UI는 0.033초마다 그 메모리를 보고 새 그림이면 복사해서 화면에 그린다.

가운데 줄 — 메인 루프(0.2초마다 한 바퀴).

  1. heartbeat.touch(): 「한 바퀴 시작했다」 표시. 이게 멈추면 감시자가 안다(7장).
  2. read_frame(): 공유 메모리에서 화면을 가져온다. 계산을 줄이려 축소 설정이 있으면 줄인다.
  3. 감지영역별 판정: 블랙·스틸(4장), 레벨미터(5장).
  4. 상태기계: 「몇 초째 이어졌나」를 세서 경보를 켤지 끌지 정한다(6장). 정파 중이면 억제.
  5. 이벤트: 경보 시작(AlarmTrigger)·해제(Resolve) 메시지를 UI로 보낸다.
  6. 남은 시간만큼 쉼: 이번 바퀴가 0.05초 걸렸으면 0.15초 쉰다. 박자가 얼마나 흔들렸는지(지터)는 진단 로그에 남긴다.

아랫줄 — 다른 일꾼들. 오디오 일꾼은 소리 크기를 재서 UI의 레벨 표시로 보낸다. 녹화 일꾼은 사고 전 10초를 늘 들고 있다가 경보 때 MP4로 만들고, 텔레그램 일꾼은 사진과 문구를 보낸다. 인터넷이 느려도 메인 루프는 기다리지 않는다.

낱말 풀이

공유 메모리 (SharedMemory)
두 프로세스가 함께 들여다보는 메모리 칸. 이름은 kbs_frame_v2, 크기 약 6.2 MB(1920×1080 화면 × 3색 = 6,220,800바이트 + 머리 정보 32바이트). 큰 그림을 매번 우편(큐)으로 복사해 보내는 것보다 훨씬 빠르다.
seqlock
잠금장치 없이 「지금 쓰는 중인지」를 번호로 알리는 방법. 쓰기 시작할 때 번호(seq)를 홀수로, 다 쓰면 짝수로 올린다. 읽는 쪽은 읽기 전과 후의 번호가 같고 짝수일 때만 그 그림을 쓴다. 다르면 쓰는 도중에 읽은 것이라 버린다.
찢어진 프레임 (torn frame)
위쪽은 새 그림, 아래쪽은 옛 그림처럼 섞인 화면. seqlock이 이걸 걸러낸다.
seq_no · .copy()
seq_no는 위의 번호. .copy()는 공유 메모리 내용을 내 메모리로 복사해 오는 것. 복사해 두면 공유 메모리가 바뀌거나 닫혀도 안전하다.
scale_factor · INTER_AREA
화면을 얼마나 줄일지 비율, 그리고 줄일 때 주변 픽셀을 평균 내는 방법(축소에 알맞은 방식).
상태기계
「정상」·「경보」 같은 상태를 기억하고, 규칙에 맞으면 다음 상태로 넘어가는 장치. 6장에서 자세히.
히스테리시스
켜는 조건과 끄는 조건을 다르게 둬서 경보가 깜빡거리지 않게 하는 것. 6장.
result_queue
Detection → UI 방향의 우편함(큐). 메시지를 차례로 넣고 꺼낸다.
지터 (jitter)
박자가 정확히 0.2초가 아니라 들쭉날쭉한 정도.
DIAG 로그
진단(diagnosis)용 기록.
RMS · dBFS
소리 크기 재는 법. 5장에서 자세히.
kbs_state_v2
상태용 작은 공유 메모리. 소리 레벨처럼 1초에 수십 번 바뀌는 값은 우편함 대신 여기에 적는다.
링버퍼
꽉 차면 가장 오래된 것부터 덮어쓰는 동그란 저장소. 늘 「최근 10초」만 들고 있다.
비유 (seqlock): 교실 게시판에 공지를 새로 붙일 때 선생님이 번호판을 「7」(홀수 = 붙이는 중)로 돌리고, 다 붙이면 「8」로 돌린다. 학생은 읽기 전에 번호를 보고, 다 읽은 뒤 다시 본다. 둘 다 「8」이면 온전한 공지를 읽은 것이고, 그사이 번호가 바뀌었으면 다시 읽는다. 선생님은 학생을 기다리지 않는다.

나올 만한 질문

Q. 왜 잠금(lock)을 쓰지 않았나?

잠금을 쓰면 한쪽이 잠근 채 멈췄을 때 다른 쪽도 기다리다 같이 멈춘다. 예를 들어 화면(UI)이 멈추면 감시까지 멈출 수 있다. seqlock은 쓰는 쪽(감시)이 절대 기다리지 않는다. 대가는 읽는 쪽이 가끔 한 프레임을 버리는 것(1프레임 지연)인데, 화면 표시에는 문제없다.

Q. 0.2초 안에 일을 다 못 끝내면?

남은 시간이 없으니 쉬지 않고 바로 다음 바퀴를 돈다. 얼마나 늦었는지는 지터로 로그에 남아 나중에 확인할 수 있다.

Q. 왜 heartbeat를 루프 맨 앞에서 찍나?

「루프가 돌고 있다」를 증명하는 게 목적이라서다. 판정 중간 어디서 멈추든 다음 touch가 안 오니 20초 뒤 감시자가 알아챈다.

쉽게 만든다면
  • 메인 루프 6칸을 「살아 있음 표시 → 화면 읽기 → 판정 → 알리기」 4칸으로 합친다(상태기계는 판정에, sleep은 빼고 말로).
  • seqlock 괄호 설명을 빼고, 「잠금 없이 번호로 온전한 그림만 읽음」 한 줄로.
  • INTER_AREA, scale_factor, DIAG는 슬라이드에서 빼도 된다(발표에서 거의 말하지 않음).
04

영상 판정 — 블랙과 스틸, 5×5 블록

어려움 ★★★약 1분 10초

감지영역 전체 평균만 보면 작은 로고나 작은 움직임이 묻혀 버린다. 그래서 25칸으로 나눠, 한 칸이라도 「정상」의 증거가 있으면 경보를 내지 않는다.

이 장이 말하는 것 — 블랙

화면 픽셀은 밝기 0(검정)~255(흰색)의 숫자다. 블랙 판정은 세 관문을 모두 통과해야 한다.

  1. 전체가 어두운가: 색 세 개(B·G·R)를 평균 내 밝기를 구하고, 밝기 5 미만인 픽셀이 98% 이상이면 1차 후보.
  2. 모든 칸이 어두운가 (블록 가드): 25칸 각각이 92% 이상 어두워야 한다. 로고가 있는 칸 하나가 블랙을 취소한다. 「로고만 떠 있는 의도된 검은 화면」을 블랙으로 잘못 잡지 않으려는 장치다.
  3. 움직임이 없는가 (모션 억제): 바로 앞 화면과 비교해 바뀐 픽셀이 0.2% 이상이면 취소. 검은 바탕에 자막이 흐르는 화면을 걸러낸다.

이 상태가 5초 이어지면 경보, 정상이 2초 이어지면 복구.

이 장이 말하는 것 — 스틸

  1. 바뀐 픽셀 찾기 (프레임 차분): 지금 화면과 바로 앞 화면을 픽셀마다 빼서, 차이가 4보다 크면 「바뀐 픽셀」로 표시한다.
  2. 모든 칸이 멈췄나: 25칸 모두 바뀐 픽셀이 10% 미만일 때만 「정지 화면」.
  3. 잠깐의 잡음 무시: 정상 화면이 3번 연속 나와야 타이머를 0으로 되돌린다. 한 번 튄 값으로 리셋되지 않게.

이 상태가 120초 이어지면 경보.

「왜 블록인가」 상자의 뜻

넓은 감지영역에서 전체 비율 하나로 보면, 화면의 몇 %를 차지하는 로고나 앵커의 입 움직임이 숫자에 거의 안 드러난다. 칸으로 나누면 그 움직임이 있는 칸 하나가 뚜렷하게 「정상」을 증명한다.

「단조 억제」는 이 블록 검사가 경보를 취소만 하고 새로 만들지는 않는다는 뜻이다. 그래서 블록 검사를 넣어도 예전보다 경보가 늘어날 수는 없다. 헛경보는 줄고, 새 헛경보는 생기지 않는다.

낱말 풀이

픽셀 · 밝기 0~255
화면을 이루는 점 하나와 그 밝기 숫자.
gray = mean(B,G,R)
파랑·초록·빨강 세 값의 평균을 밝기로 쓴다. (OpenCV는 색을 B·G·R 순서로 담는다.)
프레임 차분 |I(t) − I(t−1)|
지금 화면(t)과 바로 앞 화면(t−1)의 픽셀별 차이의 크기.
변화 마스크
바뀐 픽셀만 흰색으로 칠한 지도.
오탐 · 미탐
오탐은 사고가 아닌데 경보(헛경보), 미탐은 사고인데 못 잡음.
단조 억제
한쪽 방향(억제)으로만 작용한다는 뜻. 위 설명 참고.
비유: 교실이 조용한지 판단할 때 교실 전체 소음 평균만 재면 한 구석의 속삭임을 놓친다. 25개 모둠별로 재서 한 모둠이라도 말하고 있으면 「조용하지 않음」으로 본다.

나올 만한 질문

Q. 전체는 98%인데 칸은 왜 92%로 더 느슨한가?

추정: 한 칸은 면적이 작아서 잡음 몇 점에도 비율이 크게 흔들린다. 칸 기준을 98%로 두면 진짜 블랙도 칸 하나가 우연히 못 넘겨 취소될 수 있어 낮춘 것으로 보인다. 결정 기록을 확인하지 못했으니 단정하지 말 것.

Q. 스틸 기준이 왜 120초나 되나?

기본값이자 운영값이다. 추정: 방송에는 정지된 자막 카드·안내 화면이 꽤 길게 나오기도 해서, 짧게 잡으면 헛경보가 많아진다.

Q. 차이 4는 왜?

추정: 압축·전송 과정의 작은 잡음(픽셀 값 1~3 정도의 흔들림)을 「변화」로 치지 않으려는 문턱이다.

Q. 화면이 서서히 어두워지는 페이드아웃은?

5초 넘게 완전한 검정이 이어지지 않으면 경보가 나지 않는다. 로고가 남아 있으면 블록 가드가 취소한다.

쉽게 만든다면
  • 오른쪽 표 두 개를 지우고 「블랙: 거의 다 까맣고, 25칸 모두 까맣고, 움직임 없음 → 5초」, 「스틸: 25칸 모두 거의 안 바뀜 → 120초」 두 줄로.
  • 숫자 7개(5·98·92·0.2·4·10·3) 중 발표에는 5초·120초만 남기고 나머지는 질문용으로.
  • 왼쪽 격자 그림과 「왜 블록인가」는 그대로 — 이 장의 핵심이고 그림으로 이미 쉽다.
05

오디오 판정 — 보는 레벨미터, 듣는 임베디드

어려움 ★★☆약 1분

소리는 두 가지로 본다. 화면에 그려진 소리 막대의 초록색을 읽는 방법(채널 여러 개를 한 번에), 그리고 실제 소리 데이터의 크기를 재는 방법(정확하지만 1조).

이 장이 말하는 것 — 레벨미터(A)

  1. 감지영역의 색을 BGR에서 HSV로 바꾼다.
  2. 초록 막대 색 범위(H 40–95 · S 80–255 · V 60–255)에 드는 픽셀만 남긴다. 왼쪽 그림의 연두색이 남은 픽셀이다.
  3. 남은 픽셀 비율을 최근 5번 평균 낸다. 미터가 깜빡여도 흔들리지 않게.
  4. 5% 이상이면 「소리 있음」. 5% 미만이 60초 이어지면 경보.

그림의 A1은 실제 운영 화면에 같은 계산을 다시 해 본 결과로, 15.6%가 통과해 「소리 있음」이다.

이 장이 말하는 것 — 임베디드(EA)

  1. 캡처보드 소리를 정수(int16)로 받아 왼쪽(L)·오른쪽(R)으로 나누고 32768로 나눠 −1~1로 바꾼다.
  2. RMS로 크기를 구하고 20·log10(RMS)로 dBFS로 바꾼다. −60 아래는 −60으로 고정.
  3. L과 R의 평균이 −50 dBFS 이하로 60초 이어지면 경보. 정상 소리가 오면 바로 복구.

아래 상자는 2026-10-27 사고 이야기다. 윈도우의 「마이크 액세스」가 꺼져 캡처보드 소리 장치를 못 열었는데, 그때는 「측정값 없음」으로 처리돼 경보가 안 울렸다. 8시간 동안 소리 감시가 멈춰 있었다. 지금은 장치 열기에 실패한 시간을 「무음」으로 쳐서 무음 경보가 울리고, 60초가 지나면 시스템 알림도 보낸다.

낱말 풀이

HSV
색을 H(색상: 무슨 색), S(채도: 얼마나 선명), V(명도: 얼마나 밝은)로 나타내는 방식. 「초록만 골라내기」가 BGR보다 훨씬 쉽다.
H 40–95
OpenCV는 색상 360도를 반으로 줄여 0~179로 쓴다. 40–95는 실제 각도로 80~190도, 초록~청록 범위다.
cvtColor · inRange
색 방식을 바꾸는 명령, 그리고 범위 안 픽셀만 흰색으로 남기는 명령.
이동평균
최근 몇 개 값의 평균. 새 값이 오면 가장 오래된 값을 빼고 다시 평균.
RMS
제곱평균제곱근. 소리 파형은 +와 −를 오가서 그냥 평균하면 0이 된다. 그래서 제곱해서 평균 내고 다시 루트를 씌워 「평균 크기」를 구한다.
dBFS
디지털로 낼 수 있는 최대 크기를 0으로 둔 데시벨. 값은 늘 0 이하. −20 dBFS는 최대의 1/10, −50 dBFS는 약 0.3%.
클립
범위를 넘는 값을 끝값으로 잘라 고정하는 것.
마이크 권한
윈도우는 캡처보드 소리 입력도 「마이크」로 취급한다. 개인 정보 설정에서 마이크가 꺼지면 캡처보드 소리도 막힌다.
비유: 레벨미터 방식은 라디오 볼륨 표시등의 불빛만 보고 「소리가 나는구나」 아는 것, 임베디드 방식은 이어폰을 꽂아 직접 듣는 것이다. 불빛은 여러 대를 한눈에 볼 수 있지만 표시등이 바뀌면 다시 맞춰야 하고, 이어폰은 정확하지만 한 대만 들을 수 있다.

나올 만한 질문

Q. 레벨미터 방식의 한계는?

멀티뷰어가 그린 미터의 색과 위치에 기댄다. 멀티뷰어 설정(미터 색·배치)이 바뀌면 HSV 범위와 감지영역을 다시 맞춰야 한다. 또 「소리가 있다/없다」만 알지 잡음·찌그러짐 같은 소리 품질은 모른다.

Q. 무음 기준 −50 dBFS의 근거는?

기능 문서의 기본값이다(설정 범위 −60~0). 왜 −50인지 결정 기록은 찾지 못함 — 확인 필요. 「조용한 장면의 배경음보다는 낮고, 완전 무음(−60 근처)보다는 높게 잡았다」 정도로 답하되 단정하지 말 것.

Q. 왜 60초나 기다리나?

추정: 방송에는 의도된 짧은 무음(장면 전환, 침묵 연출)이 있어서 짧게 잡으면 헛경보가 많다.

쉽게 만든다면
  • 왼쪽 칸의 cvtColor · inRange 숫자 줄을 「초록 막대 색만 골라 비율을 셈」 한 줄로.
  • 오른쪽 칸의 ÷ 32768, 20·log10을 빼고 「실제 소리 크기를 dB로 측정 → −50 dB 이하 60초면 경보」 한 줄로.
  • 10-27 사고 상자는 남긴다 — 이야기가 있어 기억에 남는다.
06

시간축 판정 · 정파 상태기계

어려움 ★★☆약 1분 10초

0.2초마다의 판정은 경계에서 흔들린다. 그래서 「얼마나 오래 이어졌나」로 경보를 정한다. 새벽 정파는 세 가지 상태를 오가는 상태기계로 다룬다.

이 장이 말하는 것 — 왼쪽 블랙 예시

한 칸이 1초다. 윗줄은 매 순간의 판정(검정 = 블랙), 아랫줄은 실제 경보 상태다.

  • 2→7초: 블랙이 5초 이어져 경보가 켜진다.
  • 8초: 정상 화면이 한 번 끼었지만 경보는 그대로. 복구는 정상이 2초 연속이어야 한다.
  • 12→14초: 정상이 2초 이어져 복구. 텔레그램에 「지속 N초」가 간다.

켜는 조건(5초)과 끄는 조건(2초 연속)을 다르게 두는 것을 히스테리시스라고 한다. 경계값 근처에서 경보가 켜졌다 꺼졌다를 반복(플래핑)하는 걸 막는다.

이 장이 말하는 것 — 오른쪽 정파 상태기계

정파는 새벽에 송출을 멈추는 것이다. 이때 화면은 정지나 검정이라, 그냥 두면 경보가 밤새 울린다. 그래서 채널 그룹마다 1초에 한 번 상태를 검사한다.

  1. IDLE(평상시) → 00:30이 되면 [시간] PREPARATION(정파 준비)으로. 이때부터 정파를 「기다리며」 지정된 진입 감지영역을 지켜본다.
  2. PREPARATION → 진입 감지영역이 120초 넘게 스틸이면 [감지] SIGNOFF(정파 중)로. 지정된 감지영역의 알림을 끈다.
  3. SIGNOFF → 04:30 이후 30초 넘게 움직임이 이어지면 [감지], 또는 05:00이 되면 [시간] IDLE로 돌아간다.

오른쪽 아래 그림은 실제 기록이다: 00:30 준비 [시간] → 01:06 정파 [감지] → 04:45 해제 [감지].

왜 「진입은 감지만, 해제는 시간 상한」인가

KBS 정파 시작 시각은 실측으로 00:40~03:50까지 들쭉날쭉하다. 해제는 04:45~04:50 정도로 거의 일정하다.

예전에는 정해진 시각이 되면 강제로 정파 모드에 넣었다. 그런데 그날 정파가 늦으면, 그 사이 정상 방송의 경보까지 꺼 버렸다. 이것이 오진입이다. 반대로 정파를 늦게 알아채는 미진입은 헛알림 몇 개로 끝난다. 두 실수의 대가가 다르다(오류 비대칭). 그래서 들어갈 때는 반드시 화면을 보고, 나올 때는 05:00이라는 시간 상한을 둬서 정파 상태에 갇히는 일을 막았다.

진입 기준 120초에도 사연이 있다. 60초였을 때, 2026-05-18 새벽 정상 화면이 우연히 60초 멈춰 있어 01:02에 잘못 정파로 들어갔다. 그래서 120초로 늘렸다.

슬라이드에 없는 세부 (질문 대비)

2026-06-08부터 「조기 복귀」가 들어갔다. 해제 준비 시각(04:30) 전에 정파 중인 화면이 움직이기 시작하면, IDLE이 아니라 PREPARATION으로 즉시 돌아간다. 오진입을 빨리 풀되, 진짜 정파라면 다시 스틸로 들어올 수 있게 「재무장」하는 것이다(출처: docs_signoff_운영.md).

Q. 정파 중에 진짜 사고가 나면?

SIGNOFF는 「지정된」 감지영역의 알림만 끈다. 정파와 무관한 채널은 계속 감시한다. 정파 대상 채널의 사고는 정파 중이라 의미가 없다.

Q. 시간표만으로 하면 더 간단하지 않나?

정파 시작이 3시간 넘게 들쭉날쭉해서, 시간표만 쓰면 오진입(정상 방송 경보 묵살)이 생긴다. 그게 가장 비싼 실수라 감지를 택했다.

쉽게 만든다면
  • 그림이 이미 쉬워서 크게 손볼 곳은 없다.
  • 왼쪽 표 「시점 / 무슨 일」 3줄은 말로 설명하고 지워도 된다(타임라인 그림만으로 충분).
  • 아래 문장 「오진입(진짜 사고를 새벽 내내 묵살)이 미진입(헛알림 몇 개)보다 비싸다」는 꼭 남긴다 — 심사위원이 좋아할 설계 판단이다.

프로세스 격리 — Watchdog이 둘을 지킨다

어려움 ★★★약 1분 10초

Watchdog이 나머지 두 프로그램이 살아 있는지 확인한다. 오른쪽 표는 「어떤 고장을, 누가, 무엇을 보고, 몇 초 안에 알아채서, 어떻게 하는지」를 한눈에 보여 준다.

이 장이 말하는 것 — 왼쪽 상자

  • main = UI: 화면, 경보음, 경보 확인(ACK) 버튼. 공유 메모리와 우편함을 처음 만들고 소유한다. 2초마다 자기 생존 시각을 파일(ui_heartbeat.dat)에 적는다.
  • Watchdog: Detection을 띄우고, 지켜보고, 죽으면 다시 띄운다. 시스템 알림([SYSTEM])을 텔레그램으로 직접 보낸다.
  • Detection: 캡처·판정·녹화·감지 알림([DETECT]). 5초마다 heartbeat.dat를 갱신한다. 화면 라이브러리(PySide6)는 아예 불러오지 않는다.
  • IPC: 프로세스끼리 주고받는 통로. 큰 그림은 공유 메모리, 메시지는 우편함(큐). 우편함은 넣을 때 기다리지 않고(put_nowait), 가득 차면 가장 오래된 것을 버리고 넣는다. 그래서 어떤 경우에도 감시가 막히지 않는다.

이 장이 말하는 것 — 오른쪽 표, 한 줄씩

  1. Detection이 멈추거나 죽음: Watchdog이 heartbeat 파일이 10초 동안 안 바뀐 걸 보고 강제 종료 후 새로 띄운다. 새 Detection이 준비되면 UI가 지금 상태(감시 ON/OFF, 음량, 정파 상태, 감지영역)를 다시 알려 준다(재주입).
  2. 프로세스는 살아 있는데 메인 루프만 멈춤: Detection 안의 heartbeat 기록 일꾼은 따로 돌아서, 그냥 두면 계속 「살아 있음」을 적는다. 그래서 메인 루프가 20초 넘게 touch를 안 하면 기록 일꾼이 일부러 기록을 멈춘다. 그러면 1번처럼 Watchdog이 잡는다. 이때 어디서 멈췄는지 스택 덤프도 남긴다. v1의 freeze가 바로 이런 모양이었다.
  3. 계속 죽음 (반복 크래시): 뜬 지 60초 안에 또 죽으면 다시 띄우는 간격을 5→10→20초…(최대 5분)로 늘리고, 알림도 요약해서 보낸다. 알림 폭주를 막는다.
  4. UI 화면이 멈춤: UI가 2초마다 적는 시각이 30초 동안 안 바뀌면 Watchdog이 「UI 응답 없음」을 보낸다.
  5. UI 힙손상: 살아 있지만 고장 난 UI는 알림도 못 보낸다. 그래서 파일 하나만 적고, Watchdog이 대신 보낸다(9장).
  6. UI가 꺼짐: Watchdog이 10초마다 UI의 프로세스 번호가 살아 있는지 본다. 없으면 Detection을 정리하고 알린 뒤 자기도 끝낸다.
  7. 캡처 무신호: Detection이 화면 전체가 8초 동안 「검정 + 똑같음」인 걸 보고 캡처 장치만 다시 연다(최대 3회, 8장 ①).

마지막 줄: Detection을 새로 띄워도 공유 메모리·우편함은 main이 처음 만든 그대로 쓴다. 그래서 UI 화면은 끊김 없이 이어진다.

나올 만한 질문

Q. 왜 스레드가 아니라 프로세스로 나눴나?

프로세스는 메모리를 따로 쓴다. 한쪽 메모리가 망가져도 다른 쪽으로 번지지 않는다. 실제 예: UI에서 힙손상이 6번 났지만 감시(Detection)는 그동안 멀쩡히 돌았다(9장).

Q. Watchdog이 죽으면 누가 알리나?

프로그램을 끌 때 main이 Watchdog 종료를 확인하지 못하면 Detection을 정리하고 텔레그램을 직접 보낸다. 운영 중 Watchdog만 갑자기 죽는 경우를 main이 실시간으로 감시하는지는 확인 필요. 단정하지 말 것.

Q. 우편함이 가득 차서 메시지를 버리면 경보를 놓치지 않나?

가득 차는 건 UI가 오래 못 읽는 비정상 상황이다. 그때도 감시와 텔레그램 발송은 Detection 쪽에서 계속된다. 「감시가 막히는 것」보다 「화면 메시지 일부를 잃는 것」이 덜 비싸다는 선택이다.

쉽게 만든다면
  • 표 7줄을 「감시 멈춤 → 10초 안에 재시작」, 「화면 멈춤 → 30초 안에 알림」, 「화면 고장 → 다른 프로세스가 대신 알림」, 「캡처 끊김 → 8초 안에 장치만 다시 열기」 4줄로.
  • IPC 상자는 빼고 말로 한 줄.
  • 왼쪽 세 상자에서 파일 이름(ui_heartbeat.dat 등)을 빼고 「2초마다 생존 기록」처럼.

운영에서 배운 것 — 장애 3건

어려움 ★★☆약 1분 10초

세 장애 모두 「에러가 났다」가 아니었다. 「정상처럼 보이는 값」이 문제였다.

① 캡처 신호를 잃었는데 전 채널이 블랙으로 굳음 (2026-05-31 현장 보고)

보통 장치가 고장 나면 읽기 명령이 「실패(ret=False)」를 돌려준다. 그래서 「실패하면 다시 연결」 로직을 넣어 뒀다. 그런데 이 캡처보드는 신호를 잃어도 「성공」을 돌려주면서 새까만 화면을 계속 줬다. 다시 연결하는 로직이 영영 실행되지 않았다.

구별법: 진짜 방송 검정은 미세한 잡음 때문에 화면마다 조금씩 다르다. 무신호 검정은 완전히 똑같은 화면이 반복된다. 그래서 화면 전체가 8초 동안 「검정 + 직전과 똑같음」이면 캡처 장치만 다시 연다(프로그램 전체를 재시작하지 않음). 10월에 5번 일어났고, 모두 1~3초 만에 복구됐다.

교훈: 장치가 「성공」이라고 해도 믿지 말고 내용을 본다.

② 멀쩡한 Detection을 강제로 죽임 (09-15, 10-27)

예전 Watchdog은 「파일에 적힌 시각」과 「지금 시각」을 빼서 10초가 넘으면 멈췄다고 봤다. 이 PC 시계는 하루 3.5초씩 느려지고 매일 밤 인터넷 시각에 맞춰진다. 맞추기가 며칠 실패하면 한 번에 8초쯤 앞으로 뛴다. 그 순간 「10초 넘음」으로 계산돼 멀쩡한 감시를 죽였다.

지금은 파일 값이 「바뀌었는지」만 보고, 경과 시간은 Watchdog 자신의 time.monotonic()(시각 맞추기의 영향을 받지 않는 시계)으로 잰다.

교훈: 「얼마나 지났나」는 벽시계가 아니라 스톱워치로 잰다.

③ 텔레그램이 3번 감 (10-07)

사진을 보내고 답을 40초 기다리다 시간 초과(ReadTimeout)가 나면 「실패」로 보고 다시 보냈다. 그런데 사진은 이미 도착해 있었다. 그래서 같은 메시지가 세 번 갔다.

지금은 둘을 구분한다. 「답을 기다리다 시간 초과」는 상대가 받았을 수도 있으니 다시 보내지 않는다. 「보내는 도중 끊김(write timeout)」은 상대가 못 받은 게 확실하니 사진 없이 문구만 다시 보낸다.

교훈: 두 번 하면 두 번 결과가 나는 요청(비멱등)은 「상대가 받았나」를 기준으로 재시도한다.

낱말 풀이

ret=False

현재 날짜·시각. 시간 동기화 때 앞뒤로 뛸 수 있다.

컴퓨터가 켜진 뒤 흐른 시간만 세는 시계. 절대 뒤로 가거나 튀지 않는다.
ReadTimeout
요청은 보냈고, 답을 기다리다 시간이 다 된 것. 상대가 받았는지 알 수 없다.

비유: ③은 택배와 같다. 「배송 완료 문자를 못 받았다」고 같은 물건을 또 보내면 상대는 두 개를 받는다. 「트럭이 출발도 못 했다」가 확실할 때만 다시 보내야 한다.

나올 만한 질문

Q. 정파 중 진짜 검정 화면을 무신호로 착각하지 않나?

정파 중이나 사람이 감지영역을 편집하는 중에는 재오픈을 보류한다. 또 「화면 전체」가 「완전히 똑같아야」 해서 진짜 방송과 구별된다.

Q. 시계 문제는 윈도우 설정으로 고치면 되지 않나?

시계는 언제든 바뀔 수 있다(동기화, 사람이 수정, 서머타임 등). 경과 시간 측정은 시계에 기대지 않는 게 원칙적 해결이다.

쉽게 만든다면
  • 표의 「교훈」 칸을 비유로: 「성공 신호보다 내용을 본다」, 「경과 시간은 스톱워치로」, 「택배는 출발 못 한 것만 다시 보낸다」.
  • ret=False, time.time, time.monotonic()은 남겨도 된다 — 기술 심사위원에게는 오히려 반가운 정확한 이름이다.

재현 안 되는 버그 — UI 힙손상

어려움 ★★☆약 1분

4~5일마다 화면 프로그램만 조용히 고장 났다. 원인을 모르니 먼저 관측 장치를 달고, 용의자를 하나씩 빼는 실험으로 「Python 3.14 환경」을 지목했다. 3.13으로 고정한 뒤 85일째 재발이 없다.

증상

오래 켜 두면 4~5일째에 UI 프로세스에서 새 객체를 하나도 만들 수 없게 됐다. 파이썬에서 객체를 만들 때 자동으로 실행되는 함수(__init__)가 전부 TypeError를 냈다. 창은 정상처럼 보이는데 설정창·경보음·버튼이 모두 먹통이었다. 가장 나쁜 점은 일부러 다시 일으킬 수 없었다는 것(재현 불가)이다.

추적 과정 (그림의 6칸)

  1. 1~3차(05-26~): 원인을 모르니 관측부터. 죽을 때 기록(faulthandler), 고장 순간의 심층 기록, 10분마다 메모리·일꾼 수·자원 수 기록(HEALTH).
  2. 4차: 중요한 발견. 고장 난 UI는 텔레그램도 못 보냈다(requests도 객체를 만들어야 해서). 고장 상태에서도 되는 건 파일 쓰기뿐. 그래서 UI는 파일 하나만 적고 Watchdog이 대신 알린다. 42시간 동안 아무도 몰랐던 고장을 10분 안에 알게 됐다.
  3. Round 1·5차: 용의자 3개(GPU 조회, 조회 주기, 화면 버퍼)를 꺼 봤다. 그래도 재발 → 셋 다 무죄.
  4. Round 2: Python 3.14 → 3.13으로 내렸다. 13일 무사고.
  5. 6차(08-11): 재배포 때 3.13 환경이 조용히 빠져 3.14로 돌아간 상태에서 재발. 뜻하지 않게 「3.14면 재발한다」를 다시 확인한 셈(대조군).
  6. 이후 85일: 재발 0회. 이제 3.13 환경이 없으면 자동으로 다시 만들고, 기동 점검 줄에 버전을 표시한다(아래 그림 「Python 3.13.14」).

낱말 풀이

힙 (heap)
프로그램이 실행 중에 객체를 만들 때 쓰는 메모리 공간. 힙손상은 그 공간의 관리 장부가 망가진 상태.
객체 · __init__
객체는 프로그램이 다루는 하나하나의 「물건」(창, 메시지, 숫자 묶음…). __init__은 객체를 만들 때 첫 준비를 하는 함수.
TypeError
값의 종류(형식)가 맞지 않을 때 나는 오류. 여기서는 정상 코드에서 나서 「무언가 망가졌다」는 신호였다.
faulthandler
파이썬이 치명적으로 죽을 때 어디서 죽었는지 파일로 남기는 기능.
RSS · threads · handles
실제로 차지한 메모리 양 · 일꾼(스레드) 수 · 열어 둔 자원(파일·장치 등) 수.
제거 실험
용의자를 하나씩 빼고 재발하는지 보는 방법. 빼도 재발하면 무죄.
venv · 폴백
venv는 프로젝트 전용 파이썬 설치 폴더. 폴백은 원래 것이 없을 때 다른 것으로 대신 실행하는 것. 3.13 venv가 저장소에 안 올라가는 목록(gitignore)에 있어서 새로 받을 때 빠졌다.
대조군
실험에서 조건을 바꾸지 않은 비교 집단. 6차가 우연히 그 역할을 했다.
비유: 어느 집 냉장고가 4~5일마다 고장 나는데 수리기사가 와 보면 멀쩡하다. 그래서 먼저 블랙박스를 단다(관측). 그다음 콘센트를 바꿔 보고, 위치를 바꿔 보고, 하나씩 빼 본다(제거 실험). 마지막으로 전기를 다른 회로로 옮기니 멈췄다. 그런데 누가 실수로 원래 회로에 다시 꽂자 또 고장 났다(대조군). 「왜」 그 회로가 문제인지는 아직 모르지만, 그 회로를 안 쓰면 고장이 안 난다는 건 확실해졌다.

나올 만한 질문

Q. 그럼 Python 3.14의 버그인가?

모른다. 확인한 것은 「3.14 실행 환경(인터프리터 + 그에 맞춰 설치된 부품 조합)에서만 재발했다」까지다. 메커니즘은 밝히지 못했다고 솔직히 말한다.

Q. 85일이면 충분한가?

전에는 4~5일마다 났으니, 85일은 그 주기의 17~20배다. 우연히 85일 동안 안 날 가능성은 매우 낮다. 추정: 통계적으로 엄밀히 계산하지는 않았다. 「주기의 17배 넘게 무재발」로 말하면 안전하다.

Q. 감시는 그동안 괜찮았나?

고장은 UI에만 났고, Detection은 별도 프로세스라 감시와 텔레그램은 계속됐다. 프로세스 격리(7장)의 실제 효과다.

쉽게 만든다면
  • 1~3차 칸의 「faulthandler, 심층 덤프, HEALTH(RSS·threads·handles)」 → 「고장 순간을 기록하는 장치 설치」.
  • 증상 상자의 __init__·TypeError → 「새 객체를 하나도 못 만듦」.
  • 추적 6칸의 흐름(관측 → 우회 → 제거 실험 → 확인)은 그대로 — 이 장의 재미가 거기 있다.

검증 — 90일 실운영 숫자

어려움 ★☆☆약 1분

숫자는 모두 전주총국 감시PC의 실제 로그에서 셌다. 가동률은 일부러 불리하게 계산했다.

이 장이 말하는 것

  • 90일: 로그가 남아 있는 연속 운영 기간(2026-08-07~11-05). 실제 운영은 늦어도 5월부터였다.
  • 99.89%: 가동률 하한. Detection이 10분마다 남기는 HEALTH 줄의 간격이 15분을 넘는 8구간(합계 약 147분)을 전부 「멈춤」으로 쳤다. 그 대부분은 새 버전 배포 재시작이었다. 계산: 90일 = 129,600분, 147 ÷ 129,600 ≈ 0.11%.
  • 5/5: 캡처 무신호 자동 복구 5번 모두 성공, 1~3초.
  • 0원: 기존 감시PC·캡처보드 + 무료 공개 도구.
  • 자동 재기동 3회: 모두 1초 안에 사람 손 없이. 그중 2번은 시계 점프 오판(8장 ②)이었고 고쳤다.
  • 메모리: UI가 41일·44일 연속으로 떠 있는 동안 130~300 MB 안에서 오르내렸고 계속 늘어나는 추세는 없었다(메모리 누수 없음).
  • 알린 이상: 블랙 27 · 스틸 6 · 임베디드 2 · 레벨미터 1 · 무신호 5 = 41건. 대부분 모니터링·전송 장비 쪽 이상이었다. 이 기간 실제 방송사고는 없었다.
  • 확산: v1이 춘천·제주·대구·대전·부산·광주·송신인프라부 등에 배포됐다. 같은 장비에 v2로 바꿔 끼우면 된다. 설치는 실행.bat 한 번(Python 3.13·부품·ffmpeg 자동 설치). 국마다 다른 건 감지영역과 정파 시각뿐이라 설정 파일 백업·복원으로 옮긴다. 자동 테스트 107개.

Q. 실제 방송사고가 없었으면 효과를 어떻게 말하나?

자동 녹화 — 링버퍼에서 MP4까지

어려움 ★★★질문 나올 때만

사고 앞 10초와 뒤 10초를 자동으로 MP4에 담는다. 영상과 소리가 어긋나지 않게 두 가지를 맞췄다.

이 장이 말하는 것

  1. 상시 적재: 영상(JPEG 사진 묶음)과 소리(PCM)를 링버퍼에 늘 담아 둔다. 그래서 사고 「전」 10초도 남는다.
  2. 시작점 맞추기: 영상 버퍼는 「사진 몇 장」, 소리 버퍼는 「샘플 몇 개」로 크기가 정해져서, 두 버퍼가 덮는 시간이 다르다. 늦게 시작한 쪽에 맞춰 앞을 자른다. 안 그러면 파일 앞부분이 무음이 된다.
  3. 속도 보정: PC가 실제로 담은 사진 속도(실효 fps)가 설정값보다 약 6.5% 낮았다. 그대로 묶으면 영상이 빨리 재생돼 20초에 1.3초씩 어긋난다. 사진에 찍힌 시각으로 실제 속도를 재서, ffmpeg의 -itsscale로 재생 속도만 맞춘다(다시 인코딩하지 않아 빠르다).
  4. MP4 저장: 사고 뒤 10초까지. 그사이 경보가 또 나면 연장. 30일 보관.

검증: 2026-09-22 수정 뒤 실제 경보 녹화본의 첫 1초 평균 음량이 −33~−37 dB였다(무음이면 −90 dB 안팎). 앞부분 무음이 사라졌다. ffmpeg가 없으면 영상만 MP4로 저장한다.

Audio/Video. 소리와 영상의 시간을 맞추는 것(입 모양과 말소리가 맞게).

ffmpeg는 영상·소리 파일을 다루는 무료 도구. -itsscale은 입력 영상의 시간 눈금을 늘이거나 줄이는 옵션.
재인코딩
