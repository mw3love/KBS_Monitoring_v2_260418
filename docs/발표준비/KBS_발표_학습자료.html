  • 감시PC 현재 상태: 감지 ON, 경보 없음, 기록창에 빨간 ERROR 없음

1. 한눈에 — 외워 둘 것

한 줄 소개: 16채널 방송 화면과 소리를 0.2초마다 자동으로 살펴, 블랙·정지화면·오디오 이상을 화면·소리·텔레그램으로 바로 알리고, 사고 앞뒤 영상을 자동 녹화하는 무인 감시 프로그램. 프로그램 일부가 멈춰도 스스로 다시 일어선다.

2. 왜 만들었나

2-1. 빈틈 둘

  • 사람은 16채널을 24시간 볼 수 없다. 특히 새벽. 예전 전주총국 블랙 감지 프로그램은 화면이 까매지는 것만 봤고, 화면이 멈추는 것(정지화면)은 못 봤다. 실제로 정지화면 사고를 놓친 적이 있다.
  • v1(KBS Peacock v1.6.x)은 오래 켜 두면 감지가 멈췄다. 화면과 감지가 한 프로그램 안에 있어서, 화면 쪽이 멈추거나 바쁘면 감지까지 같이 멈췄다. 무인 감시에서 「감시가 조용히 멈춘 것」이 가장 위험하다. 경보가 안 울리니 아무도 모른다.

2-2. 그래서 v2에서 바꾼 것

v2는 2026-04-18에 다시 쓰기 시작했다. 핵심은 하나다. 화면·감지·감시자를 서로 다른 프로그램(프로세스)으로 나눠서, 하나가 멈춰도 나머지가 계속 돌고, 멈춘 쪽은 다른 쪽이 살려 내게 했다(3-3).

3. 어떤 원리로 도나

3-1. 영상이 들어오는 길

캡처보드 1대에 멀티뷰어(16분할 화면) 출력이 들어온다. 프로그램은 이 1920×1080 한 장을 받아, 사람이 미리 그려 둔 감지영역(사각형)만 잘라서 본다. 전주는 영상 8곳(V1~V8), 오디오 레벨미터 6곳(A1~A6), 임베디드 오디오 1곳(EA)을 본다. 소리는 캡처카드의 SDI 소리를 윈도우 오디오 장치로 받는다.

비유: CCTV 관제실에서 큰 화면 하나를 보면서, 중요한 칸마다 형광펜으로 네모를 쳐 두고 그 네모 안만 0.2초마다 확인하는 것과 같다.

3-2. 감지 4종 — 무엇을 어떻게 보나

종류판단 방법알림까지헛알림 막는 장치
블랙영역 픽셀의 98% 이상이 아주 어두움(밝기 5 이하, 0~255 기준)5초영역을 5×5칸으로 나눠 한 칸이라도 밝으면 취소(로고만 남은 의도된 검은 장면) · 자막이 흐르면 취소
정지화면(스틸)영역을 5×5 = 25칸으로 나눠, 모든 칸의 움직임이 10% 미만120초정상 프레임이 3번 연속 나와야 타이머를 리셋(순간 잡음 무시)
오디오 레벨미터화면 속 레벨미터의 초록색(HSV 색 범위) 픽셀이 5% 미만 = 소리 없음60초최근 5프레임 평균
임베디드 오디오실제 들어오는 소리(L/R 평균 RMS)가 -50dB 이하60초—
  • 시간은 모두 기본값이고 설정 「감도」 탭에서 국별로 바꾼다.
  • 복구도 기다린다(히스테리시스): 정상으로 돌아와도 블랙은 2초 이어져야 「복구」로 친다. 경계값 근처에서 알림이 켜졌다 꺼졌다 반복하지 않게 하려는 것.
  • AI(딥러닝)를 쓰지 않는다. 밝기·움직임·색 같은 규칙으로 판단한다. 그래서 가볍고, 왜 울렸는지 설명할 수 있다(로그에 「어두움 99.34%」처럼 근거가 같이 남는다).

3-3. 셋으로 나눈 구조 — 왜 안 멈추나

프로세스하는 일
화면(UI)영상 표시, 깜빡임·경보음, 버튼 조작, 설정창. 사람이 보는 부분
감지(Detection)영상·소리를 받아 0.2초마다 판정, 자동 녹화, 감지 알림 텔레그램([DETECT])
감시자(Watchdog)감지를 띄우고 지켜봄. 멈추면 다시 띄움. 시스템 알림 텔레그램([SYSTEM])
비유: 화면은 운전석 계기판, 감지는 엔진, 감시자는 옆에 앉은 정비사다. 계기판이 고장 나도 엔진은 계속 돌고, 엔진이 멈추면 정비사가 바로 다시 시동을 건다. 계기판이 먹통이면 정비사가 대신 무전(텔레그램)을 친다.
  • 감지가 10초 응답 없으면 → 감시자가 끄고 다시 띄운다. 감지는 5초마다 「살아 있음」 표시(heartbeat 파일)를 남기고, 감시자가 이걸 본다. 기동 직후 반복해서 죽으면 다시 띄우는 간격을 5→10→20초…(최대 5분)로 늘리고 알림도 줄인다.
  • 화면이 30초 멈추면 → 감시자가 「UI 응답 없음」 텔레그램. 화면은 2초마다 시각을 파일에 쓴다.
  • 화면 내부가 망가지면(힙손상) → 망가진 화면은 텔레그램조차 못 보낸다. 그래서 화면은 파일 하나(ui_degraded.flag)만 남기고, 감시자가 그걸 보고 대신 보낸다. 「보내는 주체를 나눈 것」이 핵심.
  • 화면(본체)이 죽으면 → 감시자가 10초 안에 알아채고 감지를 정리한 뒤 「전체 비정상 종료」 알림.
  • 둘 사이 데이터: 영상은 공유메모리(두 프로그램이 같이 보는 메모리 칸)로, 감지 결과·명령은 큐(우편함)로 주고받는다. 감지가 다시 떠도 화면은 그대로이고, 화면이 들고 있던 상태(감시 ON·음량·정파 상태·감지영역)를 다시 넣어 준다.

3-4. 캡처 신호가 끊겼을 때

캡처보드는 입력 신호를 잃으면 오류를 내지 않고 「정상인 척」 완전히 까만 화면을 계속 보낸다. 예전엔 사람이 프로그램을 다시 켤 때까지 전 채널이 블랙으로 굳어 있었다(2026-05-31 현장 보고). 지금은 화면 전체가 8초 넘게 「까맣고 + 똑같이 멈춰」 있으면(진짜 방송 검정은 미세한 잡음이 있어 매번 조금씩 다르다) 캡처 장치만 다시 연결한다. 최대 3번 시도하고, 블랙 알림·녹화는 그대로 남긴다. 10월 실제 5번: 10-03 2초 · 10-04 3초 · 10-21 3초 · 10-27 1초 · 10-30 1초. 화면 전체가 꺼질 때는 채널별 16통 대신 「전체 화면」 한 통으로 묶어 보낸다.

3-5. 정파(Sign-off) 자동 처리

새벽 정파 시간에는 화면이 멈추거나 검은 게 정상이라, 그대로 두면 경보가 쏟아진다. 그래서 그룹(예: 1TV·2TV)별로 세 상태를 자동으로 오간다.

상태뜻넘어가는 조건
대기평소정파준비 시각(예: 00:30)이 되면 → 정파준비
정파준비곧 정파. 정지화면 알림은 억제, 블랙은 계속 알림지정한 감지영역이 120초 넘게 멈추면 → 정파 (진입은 화면 감지로만). 운영값 120초 — 60초였을 때 2026-05-18 01:02에 정상 화면이 60초 스틸로 잡혀 잘못 진입해서 올림. 기능 레퍼런스의 기본값 표에는 5초로 적혀 있지만 운영 설정은 120초
정파지정한 감지영역의 텔레그램을 막음해제준비 구간(예: 04:30~)에 화면이 30초 움직이면, 또는 끝 시각(05:00)에 → 대기 (해제는 시간 기준)

정파 시작은 실측 00:40~03:50으로 불규칙하고, 해제는 04:30 이후로 거의 고정이다(실측 2TV 04:45 · 1TV 04:50). 예전엔 시간이 되면 강제로 정파 모드에 넣었는데, 실제 정파가 늦으면 그 사이 정상 방송의 경보를 묵살했다. 오류 비대칭: 오진입(정파 아닌데 정파 모드)은 진짜 사고를 새벽 내내 묵살해 나쁘고, 미진입(정파인데 정파 모드 아님)은 헛알림 몇 개라 가볍다. 그래서 진입은 감지 단독, 해제는 시간 상한으로 바꿨다(2026-06-07, 근거: docs_signoff_운영.md §1·§3·§6). 정파 관련 텔레그램은 진입 1통 + 해제 1통. 90일 동안 정파 진입 124번 / 해제 111번을 알렸다.

3-6. 알림과 녹화

  • 화면·소리: 이상 난 감지영역이 0.5초 간격으로 깜빡이고 경보음. 「알림 확인(ACK)」을 누르면 멈추고, 같은 이상이 계속돼도 다시 울리지 않는다. 이상이 풀리면 다음 이상부터 다시 울린다.
  • 텔레그램: 채널 사진(16분할 전체)과 시각·채널·종류. 복구되면 「지속 N초」. 같은 채널은 60초 안에 중복 발송 안 함. 실패하면 2번 다시 시도하고, 보내는 일을 맡은 스레드가 죽으면 자동으로 되살린다.
  • 자동 녹화: 항상 최근 10초를 메모리에 들고 있다가, 알림이 나면 그 10초 + 이후 10초를 MP4로 저장(ffmpeg로 소리 합성). 녹화 중 또 알림이 나면 같은 파일을 늘린다. 30일 지나면 자동 삭제. 녹화본에는 원본 16분할 화면만 담기고 프로그램 화면은 안 담긴다.

3-7. 판정 연산 세부 (슬라이드 4·5)

판정코드에서 하는 연산 (detection/detector.py, audio_monitor.py)
블랙ROI crop → gray = crop.mean(axis=2)(B·G·R 평균, cvtColor 아님) → gray < 5 비율 ≥ 98% → 5×5 블록 각각 ≥ 92%(하나라도 미달이면 취소) → 직전 프레임 대비 변화 픽셀 ≥ 0.2%면 취소
스틸diff = |crop(t) − crop(t−1)|(float32, BGR 채널별) → diff > 4 = 변화 마스크 → 25블록 중 하나라도 변화 ≥ 10%면 「움직임」. 블록 경계는 np.linspace로 균등 분할
레벨미터cv2.cvtColor(BGR→HSV) → cv2.inRange([40,80,60], [95,255,255]) → 통과 픽셀 비율 → deque(maxlen=5) 이동평균 ≥ 5%면 활성. OpenCV의 H는 0~179라 40~95 ≈ 일반 색상환 80°~190°(연두~청록)
임베디드int16 PCM ÷ 32768 → L·R 각각 sqrt(mean(x²)) → 20·log10 → −60~0 dB 클립 → (L dB + R dB)/2 ≤ −50

A1 실측 15.6%는 발표 자료용으로 운영 화면 캡처(docs/소개서/main.jpg, 화면 오버레이 포함)에 같은 연산을 돌려 다시 계산한 값이다. 실제 판정은 오버레이 없는 원본 프레임에서 한다. 블록 격자 그림도 같은 캡처에 격자만 그린 것이다(블랙·스틸 실제 판정 장면의 녹화본은 없음).

3-8. 프로세스 사이 통신 세부 (슬라이드 3·7)

  • seqlock: 공유메모리 헤더 맨 앞 8바이트가 seq_no. 쓰는 쪽은 홀수로 바꾸고 → 픽셀 복사 → 짝수로. 읽는 쪽은 읽기 전 seq가 홀수면 포기, 읽은 뒤 seq가 바뀌었으면 「찢어진 프레임」이라 버린다(최악 1프레임 건너뜀). 락이 없어서 한쪽이 멈춰도 다른 쪽이 기다리다 같이 멈추지 않는다. 크기: 헤더 32 B + 1920×1080×3 = 6,220,832 B.
  • Queue: result_queue(Detection→UI, 200칸), cmd_queue(UI→Detection, 50칸). 넣을 땐 put_nowait, 가득 차면 가장 오래된 것 하나를 빼고 넣는다 → 절대 블로킹되지 않는다.
  • heartbeat 2단: Detection 안의 writer 스레드가 5초마다 파일에 시각을 쓴다. 단 메인 루프가 20초 넘게 touch()를 안 하면 쓰기를 멈춘다 → 「프로세스는 살았는데 루프만 멈춘」 경우도 잡힌다. Watchdog은 값이 10초 안 바뀌면 kill·재spawn.
  • 재spawn 뒤 상태 복원: 새 Detection은 설정 파일을 스스로 읽고 뜬 뒤 DetectionReady를 보낸다. UI는 그때 감지 ON/OFF·음량·음소거·정파 상태·ROI를 다시 넣어 준다. 경보 ACK 상태는 UI에만 있다.
  • 반복 크래시 백오프: 기동 60초 안에 죽으면 「빠른 중단」으로 세고 간격을 5→10→20초…최대 5분으로 늘린다. 4회째부터 알림은 요약 1통, 60초 정상이면 「안정화」 1통.

3-9. 운영 장애 3건 (슬라이드 8)

사건무슨 일이었나 · 어떻게 고쳤나
캡처 무신호캡처보드는 신호를 잃어도 cap.read()가 True와 새까만 프레임을 준다. 「읽기 실패 시 재연결」 로직이 안 걸려 사람이 재시작할 때까지 전 채널 블랙. 구분법: 진짜 방송 검정은 미세 잡음으로 프레임마다 조금씩 다르고, 무신호 검정은 똑같은 프레임 반복. 전체 화면을 축소해 최댓값이 거의 0이고 직전 프레임과 같으면 「얼어붙은 검정」, 8초면 장치만 재오픈(관찰 5초, 최대 3회, 이후 60초 쿨다운). 정파 중·ROI 편집 중·파일 재생 중엔 보류. 코드: detection/capture_watchdog.py.
시계 점프 오판이 PC 시계는 하루 약 3.5초 늦고, 윈도우 시간 동기화가 며칠 실패하면 한 번에 8초쯤 앞당겨진다. 예전 Watchdog은 「파일에 적힌 시각 − 지금 시각」으로 판정해서 멀쩡한 Detection을 10초 초과로 보고 죽였다(09-15 8.5초, 10-27 7.9초). 지금은 파일 값이 바뀌었는지만 보고, 경과 시간은 Watchdog 자신의 time.monotonic()으로 잰다. monotonic = 벽시계 조정과 무관하게 앞으로만 가는 시계. 코드: watchdog_process.py HeartbeatAgeTracker.
텔레그램 3중 발송사진 올린 뒤 응답을 40초 기다리다 ReadTimeout → 재전송. 그런데 요청은 이미 텔레그램에 도착해 있어서 같은 메시지가 3번 갔다(10-07 정파 해제, 세 통 모두 같은 시각 값). 텔레그램 sendMessage는 같은 요청을 두 번 보내면 두 번 올라가는 비멱등 요청이다. 그래서 응답 timeout은 「보냈는지 모름」이라 재전송하지 않고, 요청 본문을 보내다 끊긴 경우(write timeout)만 사진 없이 다시 보낸다.

3-10. 자동 녹화 A/V 동기 (부록)

영상 버퍼는 「프레임 개수」, 오디오 버퍼는 「샘플 수」로 크기가 정해져서 덮는 시간이 서로 다르다. 그대로 합치면 그 차이만큼 파일 앞부분이 무음이 됐다 → 두 버퍼의 시작점을 늦은 쪽에 맞춰 자른다(2026-09-22). 또 영상이 실제로 쌓이는 속도(실효 fps)가 출력 fps보다 낮아, 그대로 묶으면 영상이 약 6.5% 빨리 재생돼 20초당 1.3초씩 소리와 어긋났다 → 프레임 타임스탬프로 실효 fps를 재서 ffmpeg -itsscale로 시간 축만 바꾼다(재인코딩 없음). 보정 계수가 0.5~4.0 밖이면(시계 점프 등) 보정하지 않는다.

6. 개발 이야기 — 질문 나오면 꺼낼 것

6-1. 화면 힙손상 추적(6번 재발 → 85일 0회)

오래 켜 두면 4~5일째마다 화면만 조용히 고장 나 설정창·경보음이 먹통이 되는 일이 6번 있었다(05-26 ~ 08-11). 창은 멀쩡해 보여서 더 위험했다. 재현이 안 돼 용의자를 하나씩 빼는 「제거 실험」으로 좁혔다.

  1. 1~3차: 고장 순간을 기록하는 장치를 심음.
  2. 4차: 고장 난 화면은 텔레그램도 못 보낸다는 걸 발견 → 감시자가 대신 보내도록 구조를 바꿈(42시간 방치 → 10분 안에 통보).
  3. Round 1: GPU 조회 등 용의자 3개를 끔 → 5차 재발 → 무죄.
  4. Round 2: Python 3.14 → 3.13으로 내림 → 13일 무사고.
  5. 6차(08-11): 재배포 때 3.13 환경이 조용히 빠져 3.14로 돌던 걸 찾음 → 결론 재확인. 지금은 빠지면 자동으로 다시 설치하고 경고를 남김.
  6. 이후 85일 재발 0회.

7. 예상 질문과 답

Q1. 멀티뷰어나 상용 감시 장비에도 알람 기능이 있지 않나?
있는 장비도 있다(추정: 기종별 기능은 확인 필요). 이 프로그램의 차이는 ① 이미 있는 감시PC·캡처보드에 비용 0원으로 붙는다 ② 정파처럼 KBS 운영에 맞춘 처리 ③ 텔레그램 사진·자동 녹화로 자리에 없어도 알고 증거가 남는다 ④ 프로그램이 멈추면 스스로 살아난다.
Q2. 헛알림(오탐)은 얼마나 되나?
헛알림을 줄이는 장치를 여럿 넣었다: 로고만 남은 검은 장면 구분(5×5칸 검사), 흐르는 자막 구분, 복구 대기, 정파 중 억제, 전체 화면 블랙은 한 통으로 묶기. 90일 동안 알린 이상은 대부분 장비 쪽 실제 이상이었다. 「헛알림 비율」을 따로 센 숫자는 없다(확인 필요 — 정직하게 「따로 세지 않았다」고 답).
Q3. 놓친 사고(미탐)는 없나?
이 기간 실제 방송사고가 없어서 「실제 사고를 잡았다」는 실증은 아직 없다. 대신 장비 이상(블랙·정지·무음·신호 끊김)은 새벽에도 알렸고 녹화가 남았다. 감지 자체가 멈추는 경우는 감시자가 10초 안에 잡는다.
Q4. 왜 AI(딥러닝)를 안 썼나?
블랙·정지·무음은 밝기·움직임·소리 크기로 충분히 정확히 판단된다. 규칙 기반이라 가볍고(일반 감시PC), 왜 울렸는지 숫자로 설명할 수 있고, 학습 데이터가 필요 없다.
Q5. 다른 총국에 어떻게 까나? 개발자가 가야 하나?
안 가도 되게 만들었다. 저장소를 받아 실행.bat을 누르면 설치까지 자동. 국마다 다른 건 감지영역(화면 배치)과 정파 시각뿐이라, 설정창에서 그리고 저장/불러오기로 백업한다. 사용안내가 프로그램 안(「?」)에 있다.
Q6. 왜 프로그램을 셋으로 나눴나? 하나면 더 간단하지 않나?
v1이 한 덩어리라 화면이 멈추면 감지도 멈췄다. 나누면 하나가 멈춰도 나머지가 돌고, 멈춘 쪽을 다른 쪽이 살린다. 특히 고장 난 화면은 알림을 못 보내니 보내는 쪽을 따로 둬야 했다(6-1).
Q7. 텔레그램이 안 되면(인터넷 끊김)?
화면 깜빡임·경보음·녹화는 인터넷과 상관없이 동작한다. 텔레그램은 2번 재시도하고, 실패는 기록창 ERROR에 남는다.
Q8. 16채널보다 많이 볼 수 있나?
캡처보드에 들어오는 한 화면 안에서 감지영역을 원하는 만큼 그리는 구조라, 「채널 수」보다 「멀티뷰어 화면에 몇 개가 보이느냐」가 한계다. 전주는 지금 영상 8 + 레벨미터 6 + 임베디드 1을 본다.
Q9. PC 사양은 얼마나 필요한가?
전주 감시PC 기준 CPU 사용률 50% 안팎(운영 화면 캡처). 정확한 최소 사양은 확인 필요. 느린 PC는 감도설정의 「자동 성능 감지」가 주기·해상도를 낮춰 맞춘다.
Q10. 오래 켜 두면 메모리가 새지 않나?
세 프로세스가 10분마다 메모리·스레드 수를 기록한다. 화면 프로세스가 41일·44일 연속 가동하는 동안 늘지 않았다. 원하면 예약 재시작으로 정해진 시각에 스스로 다시 켤 수도 있다.
Q11. 감시PC가 아예 꺼지면?
PC 자체가 꺼지는 건 프로그램이 알릴 수 없다(그땐 알림이 아예 안 오는 것으로 알게 된다 — 「살아 있음」을 따로 보내는 기능은 없음). 프로그램 본체(화면)만 죽으면 감시자가 「전체 비정상 종료」 텔레그램을 보낸다. 이때 자동으로 다시 켜지지는 않는다 — 실행.bat은 예약 재시작(종료코드 42)일 때만 다시 켠다.
Q12. 개발 기간·방법은?
2026-04-18 시작, 업무와 병행. 커밋 203번, 약 18,000줄, 자동 테스트 107개. 고장은 기록(fix/ 폴더 6건)을 남기며 추적했다. (AI 코딩 도구 사용을 어떻게 말할지는 발표자가 정할 것.)
Q13. 공유메모리에 왜 락(Lock)을 안 쓰나?
쓰는 쪽 하나(캡처 스레드), 읽는 쪽 둘(UI·메인 루프)이고 1프레임 지연은 괜찮다. 락을 쓰면 한쪽이 락을 쥔 채 멈췄을 때 다른 프로세스까지 같이 멈출 수 있다 — 격리한 의미가 사라진다. seqlock은 읽는 쪽이 「찢어진 프레임」을 알아채고 버리기만 하면 된다.
Q14. 왜 스레드가 아니라 프로세스로 나눴나?
스레드는 같은 메모리·같은 인터프리터를 쓴다. 힙이 망가지거나 인터프리터가 멈추면 모든 스레드가 같이 죽는다. 프로세스는 메모리가 분리돼 한쪽 손상이 다른 쪽으로 번지지 않고, 밖에서 kill·재spawn할 수 있다. (추정: v1 freeze의 정확한 원인은 특정하지 않았다 — 원인 하나를 고치기보다 구조로 격리했다고 답한다.)
Q15. HSV를 쓴 이유는? RGB로는 안 되나?
HSV는 색상(H)과 밝기(V)가 분리돼 「초록색인가」를 밝기와 상관없이 고를 수 있다. RGB로 초록을 고르려면 세 채널의 비율 조건을 써야 하고, 미터가 어두운 초록·밝은 초록으로 바뀔 때 기준이 흔들린다.
Q16. 블랙 기준 「밝기 5」는 너무 낮지 않나? 방송 블랙은 16(limited range)일 텐데?
확인 필요. 캡처보드·드라이버가 0~255 full range로 넘기는지 16~235로 넘기는지에 따라 달라진다. 운영에서 「어두움 99.34%」처럼 알림마다 비율이 로그에 남아, 그 분포를 보고 기준을 맞춰 왔다. 기준은 감도 탭에서 바꿀 수 있다.
Q17. 힙손상 원인이 Python 3.14라는 근거는?
단정하지 않는다. 3가지 용의자를 하나씩 끄는 동안은 재발, 인터프리터만 3.13으로 바꾸자 무사고, 그런데 재배포 실수로 3.14로 돌아갔을 때 다시 재발(의도치 않은 대조군), 3.13 고정 후 85일 0회. 「3.14 실행 환경에서만 재발한다」까지가 증거이고 내부 메커니즘은 미규명.
Q18. 보안 — 외부로 영상이 나가나?
밖으로 나가는 건 텔레그램 알림(사진 1장·문구)뿐이다. 받는 사람은 설정한 채팅방으로 한정된다. 녹화는 감시PC 안에만 저장된다.
