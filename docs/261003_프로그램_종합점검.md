## 1단계 — 정적 점검 (코드 수정 없음)

사용 도구: `ruff 0.16.10`, `vulture 2.16`(scratchpad의 별도 venv에 설치해 시스템 Python은 건드리지 않음), 설정 키·IPC 메시지 대조 스크립트, 코드 직접 읽기.

### 발견한 문제

#### [상] F1. 감지 메인 루프가 멈추면 아무도 모른다 — 확정(구조), 실제 발생은 미재현

v1을 다시 만든 이유가 "감지 루프 freeze"였는데, v2에도 이걸 잡는 장치가 없다.

- `HeartbeatWriter`(`processes/detection_process.py:30`)는 **별도 스레드**라서, 메인 루프가 멈춰도 5초마다 계속 `heartbeat.dat`를 쓴다. 그래서 Watchdog은 멈춘 걸 모른다.
- 메인 루프가 감시하는 건 **영상 캡처 스레드**뿐이다(`detection_process.py:600` `video_worker.loop_age_sec()`). 메인 루프 자기 자신은 감시 대상이 아니다.
- UI의 "감지 중단 — 루프 응답 없음" 표시(`ui/top_bar.py:508`)는 `DiagSnapshot`의 `loop_count == 0`일 때 켜진다(`ui/main_window.py:424`). 그런데 그 DIAG를 보내는 게 바로 그 메인 루프다. 그래서 루프가 멈추면 DIAG도 안 오고, 표시는 영원히 "정상"으로 남는다. 루프가 돌고 있으면 카운터가 항상 1 이상이라서, 사실상 이 표시는 켜질 일이 없다.
- 현재 유일한 흔적은 10분마다 찍히는 HEALTH 로그가 끊기는 것이다(`detection_process.py:549` 주석). 사람이 나중에 로그를 봐야만 알 수 있다.
- 3단계에서 메인 루프에 인위적인 멈춤을 넣어 재현할 계획이다.

#### [상] F2. "알림음 지속(초)" 설정 4개가 아무 효과가 없다 — 확정

- 설정창 감지설정 탭의 블랙·스틸·오디오레벨·임베디드 `알림음 지속(초)`(1~300, 기본 60)는 저장되고(`settings_dialog.py:1924` 등) Detection의 `detector.*_alarm_duration`에도 들어간다(`detection_process.py:122` 등). 하지만 그 값을 **읽는 코드가 없다**.
- 실제로 소리를 내는 `AlarmSystem.trigger()`는 `alarm_duration` 인자를 받을 수 있게 만들어져 있다(`ui/alarm.py:67`). 그런데 호출하는 쪽(`ui/main_window.py:271`)이 그 인자를 넘기지 않아서 항상 0이 된다. 0이면 "무제한"이라 알림음은 확인 버튼이나 복구 때까지 계속 울린다.
- `AlarmTrigger` 메시지에도 지속시간 필드가 없다. 그래서 고치려면 메시지 스펙(`docs_ipc_spec.md`)부터 바꾸거나, UI가 자기 설정에서 값을 읽어야 한다.
- **확인 필요**: 지금처럼 "확인할 때까지 계속 울림"이 운영 의도라면, 고칠 게 아니라 설정 항목을 지우는 게 맞다.

#### [중] F3. 테스트가 운영 Python에서 돌지 않는다 — 확정

- 운영 실행 환경은 `.venv313`(Python 3.13.14)인데, 거기엔 `pytest`가 없다. 테스트 76개는 시스템 Python 3.14.2에서만 통과를 확인했다.
- 6차 힙손상의 원인이 Python 3.14 계열이었다는 점을 생각하면, 테스트 환경과 운영 환경이 다른 건 맹점이다.

#### [중] F4. Detection이 반복해서 죽으면 재시작과 텔레그램이 무한 반복된다 — 확정(코드), 영향은 추정

- Watchdog은 재spawn 사이에 고정 5초(`_SPAWN_COOLDOWN`, `watchdog_process.py:52`)만 쉬고, 횟수 제한이나 점점 늘어나는 대기(backoff)가 없다.
- 기동 직후 바로 죽는 상황(예: 캡처 드라이버 오류, 설정 파일 손상)이면, 몇 초마다 "중단 감지"와 "재spawn 완료" 텔레그램 2통이 끝없이 나간다(추정: 실제 간격은 기동 시간에 따라 다름).

#### [중] F5. 설정창 숫자 칸 일부에 입력 검사가 없어 저장이 조용히 실패할 수 있다 — 코드상 확인, 실행 재현 전

- `_float_edit()`(`settings_dialog.py:78`)는 검사기(validator)가 없다. 그래서 소수 칸 8곳(예: 어두운 픽셀 비율)에 `abc`나 `1.2.3`을 넣으면 저장 때 `float()`가 실패한다(`settings_dialog.py:1920` 등).
- 음수를 허용하는 정수 칸(임베디드 무음 임계값 -60~0)은 `-`만 입력한 상태가 통과될 수 있어 `int("-")`가 실패한다(추정).
- 실패하면 예외가 ui 로그에만 남고 화면에는 아무 안내가 없다(추정: 저장 버튼을 눌러도 반응 없이 끝남). 3단계에서 직접 입력해 재현한다.

#### [중] F6. `requirements.txt` 주석이 위험한 버전을 권한다 — 확정

- 주석에 "전주총국 운영 환경: 3.14.2"라고 적혀 있다. 지금 운영 기준은 3.13(`.venv313`)이고, 3.14는 힙손상 원인으로 지목된 버전이다. 새로 설치하는 사람이 이 주석을 보고 3.14를 고를 수 있다.

#### [하] F7. 디스크 보호가 일수 기준뿐이다 — 확정

- 녹화 파일은 `max_keep_days`(기본 30일)로만 지운다. 디스크 여유 공간은 보지 않는다. 알람이 몰리는 날 디스크가 가득 차면 녹화와 로그 쓰기가 같이 실패할 수 있다(추정).
- 로그(`logs/YYYYMMDD_*.txt`)는 지우는 코드가 없어 계속 쌓인다(하루 크기가 작아 당장 문제는 아님).

#### [하] F8. 기타 작은 것

- `자동 성능 감지` 버튼이 UI를 1초 동안 멈춘다(`settings_dialog.py:2193` `cpu_percent(interval=1.0)`).
- `watchdog_process.py`의 "UI 생존 확인 (30초 주기)" 주석과 달리 실제 값은 10초다(`_PARENT_CHECK_SEC`).
- `ruff` 기준으로 안 쓰는 import 20개, 안 쓰는 변수 몇 개(`watchdog_process.py`의 `last_hb_value`, `settings_dialog.py:1614`의 `emb` 등)가 있다.

### 불필요한 것 (정리 후보)

지우기 전에 한 번 더 확인이 필요하다. `vulture`는 60% 신뢰도라 오탐이 섞이고, Qt가 이름으로 부르는 메서드(`paintEvent` 등)는 이미 목록에서 뺐다.

- **안 쓰는 IPC 메시지**(어디서도 보내지 않음):
  - `DetectionResult`(UI가 받을 준비만 함)
  - `PauseForRoiEdit`, `RequestSnapshot`(보내지도 처리하지도 않음)
  - `RequestAutoPerf` → `_handle_auto_perf()` → `PerfMeasurement` 경로 전체. 설정창 버튼은 UI 안에서 따로 측정한다. 이 죽은 경로를 나중에 연결하면 감지 루프를 최대 10초 재우니, 지우는 게 안전하다.
  - 지울 때는 `docs_ipc_spec.md`와 `tests/test_ipc_contract.py`도 같이 바꿔야 한다.
- **v1에서 넘어온 안 쓰는 메서드**: `roi_manager`의 add/remove/copy 6개, `signoff_manager`의 조회 메서드 4개, `alarm.set_sounds_dir`·`get_sound_files`, `top_bar._fmt_elapsed`, `shared_state.is_ready`·`get_write_seq`, `telegram_worker.test_connection`.
- **F2와 묶이는 것**: `detector.*_alarm_duration`, `detector.embedded_silence_threshold` 속성(값만 넣고 안 읽음).

### 확인했고 문제없던 것

- 이름 오타나 정의 안 된 변수(`ruff F821`)는 0건이다.
- `default_config.json`의 설정 키와 코드가 읽는 키가 일치한다.
- 실제로 쓰는 IPC 메시지는 보내는 쪽과 받는 쪽의 짝이 전부 맞다.
- `except Exception: pass` 류(Detection·Watchdog·main 쪽 40곳)를 표본으로 읽어 봤다. 대부분 "로그 쓰기마저 실패할 때의 대비"나 "임시 파일 정리"라서 의도된 것이고, 장애를 숨기는 위험한 삼킴은 찾지 못했다.
- 테스트 76개는 3.14에서 전부 통과한다.
