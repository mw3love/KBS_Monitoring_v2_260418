v1을 다시 만든 이유가 "감지 루프 freeze"였는데, v2에도 이걸 잡는 장치가 없다.

- `HeartbeatWriter`(`processes/detection_process.py:30`)는 **별도 스레드**라서, 메인 루프가 멈춰도 5초마다 계속 `heartbeat.dat`를 쓴다. 그래서 Watchdog은 멈춘 걸 모른다.
- 메인 루프가 감시하는 건 **영상 캡처 스레드**뿐이다(`detection_process.py:600` `video_worker.loop_age_sec()`). 메인 루프 자기 자신은 감시 대상이 아니다.
- UI의 "감지 중단 — 루프 응답 없음" 표시(`ui/top_bar.py:508`)는 `DiagSnapshot`의 `loop_count == 0`일 때 켜진다(`ui/main_window.py:424`). 그런데 그 DIAG를 보내는 게 바로 그 메인 루프다. 그래서 루프가 멈추면 DIAG도 안 오고, 표시는 영원히 "정상"으로 남는다. 루프가 돌고 있으면 카운터가 항상 1 이상이라서, 사실상 이 표시는 켜질 일이 없다.
- 현재 유일한 흔적은 10분마다 찍히는 HEALTH 로그가 끊기는 것이다(`detection_process.py:549` 주석). 사람이 나중에 로그를 봐야만 알 수 있다.

### [상·신규] F10. Detection이 강제 종료되면 UI가 영구히 멈춘다 — 재현 확정

이번 점검에서 가장 심각한 문제다.

- **증상**: Detection을 강제 종료한 직후 UI가 완전히 멈췄다. 화면 시계가 16:24:13에서 멈추고, 영상 갱신·로그·창 닫기가 모두 반응하지 않았다. 알림음과 조작도 당연히 안 된다. Detection·Watchdog·텔레그램은 계속 돌아서 겉으로는 알아채기 어렵다.
- **스택**(`py-spy dump`): UI 메인 스레드가 `_on_detection_ready` → `_reinject_runtime_state` → `_send_cmd`(`ui/main_window.py:685`) → `cmd_event.set()` → `multiprocessing.Condition.notify()` 안에서 멈춰 있다.
- **원인**: `cmd_event`는 `multiprocessing.Event`다(`main.py:264`). Detection 메인 루프는 대부분의 시간을 `cmd_event.wait()`(`detection_process.py:790`)에서 보낸다. 기다리는 도중 강제 종료되면 "자는 사람 수"가 1 남은 채로 남는다. 이후 누군가 `set()`을 부르면, 이미 죽은 프로세스가 "깼다"고 답하기를 영원히 기다린다.
- **독립 재현**: 앱과 무관한 20줄짜리 스크립트(waiter를 `terminate()` → `set()`)로 5번 중 5번 멈췄다. 그래서 우연이 아니라 구조 문제다.
- **운영 영향**: 윈도우에서 Watchdog의 `_kill_detection()`이 쓰는 `proc.terminate()`도 똑같은 강제 종료다. 그래서 heartbeat stale로 재spawn하든, Detection이 네이티브 크래시로 죽든, 재spawn 직후 UI가 `DetectionReady`를 받아 상태를 재주입하는 순간 멈출 가능성이 높다(추정: 종료 순간 Detection이 `wait()` 안에 있을 확률이 높다는 전제).
- **도입 시점**: `e0f30ca`(2026-04-23, "cmd_event로 포트변경 Detection 지연 개선")부터 있었다.
- **확인 필요**: 운영 PC에서 재spawn이 실제로 일어난 적이 있는지, 그때 UI가 멈췄는지. 감시PC의 `logs/*_watchdog.txt`에서 `재spawn 완료`를 찾아보면 된다.
- **관련 위험(추정, 미재현)**: `cmd_queue`도 Detection 재spawn을 넘어 재사용된다. Detection이 `get_nowait()`로 큐 내부 잠금을 잡은 찰나에 죽으면, 새 Detection이 명령을 영영 못 받을 수 있다. 창이 아주 짧아 확률은 낮다.

## 수정 기록

### F10 수정 (2026-10-03)

- `cmd_event`(`multiprocessing.Event`)를 없앴다. 대신 Detection은 루프 대기 중 20ms(`_CMD_POLL_SEC`)마다 `cmd_queue.empty()`를 확인하고, 명령이 있으면 바로 깬다. 명령 반응 지연의 상한은 20ms다.
- 같은 종류의 위험인 `state_lock`(`multiprocessing.Lock`)도 없앴다. 공유 상태에 쓰는 쪽은 Detection 하나뿐이라, Detection 안의 `threading.Lock`으로 바꿨다. 독립 스크립트에서, 잠금을 쥔 프로세스를 죽이면 다음 사람이 3초 안에 잠금을 얻지 못하는 것을 확인했다.
- 검증(프록시검증, 개발 PC, 3.13.14):
  - 단위 테스트 76개 통과.
  - `tests/test_chaos.py --rounds 4` 4/4 통과. 이번에 매 라운드 "UI처럼 명령을 보내고, 새 Detection이 처리했는지(`shared_state` 반영)" 확인하는 단계를 추가했다.
  - 실제 앱에서 45초 동안 Detection을 10번 강제 종료했다. 수정 전에는 첫 번째 종료에서 UI가 영구 정지했는데, 수정 후에는 10번 모두 재spawn과 상태 재주입이 끝났고 UI가 계속 반응했다(화면 시계가 실제 시각과 일치하고, `py-spy`로 본 UI 메인 스레드가 프레임을 그리는 중). 마지막에 창 닫기로 정상 종료했다(`last_exit.json` 갱신, Watchdog "의도된 종료").
- 미검증: 20ms 폴링으로 인한 CPU 사용량 변화(측정하지 않음, `empty()`는 파이프 상태만 보는 가벼운 호출이라 영향은 작다고 추정). 감시PC 실조건 확인.
- 남은 관련 위험(추정, 미수정): `cmd_queue` 내부의 읽기 잠금을 Detection이 쥔 찰나에 죽는 경우. 창이 매우 짧아 이번에는 고치지 않았다.

### P1. UI 멈춤 감시 (추천 1순위)

- **문제**: Watchdog은 UI가 "살아 있는지"(`psutil.pid_exists`)만 본다. 오늘 F10처럼 UI가 멈춰도 프로세스는 살아 있으니 아무도 모른다. 현장 경보음과 화면이 죽은 채로 남는다. 힙손상 사고 6번도 모두 "UI만 망가지고 나머지는 정상"이었다.
- **방법**: UI의 기존 33ms 프레임 타이머(또는 1초 타이머)가 `data/ui_heartbeat.dat`에 시각을 쓴다. Watchdog이 기존 1초 루프에서 30초 이상 묵으면 `[SYSTEM]` 텔레그램 "UI 응답 없음 — 현장 경보음이 울리지 않습니다"를 1회 보낸다. 이미 있는 `ui_degraded.flag` 경로와 같은 모양이라 새 구조가 필요 없다.
- **주의**: 처음에는 알림만 보낸다. UI 자동 재시작은 화면 상태·ROI 편집 중 등 고려할 게 많아 별도 판단이 필요하다.

### P2. 기동 자가진단 알림

- **문제**: CLAUDE.md "신규 빌드 배포 시 함정" 항목들(설정 미복원, `.venv313` 누락으로 3.14 폴백, `notify_system` 꺼짐, ffmpeg 없음)은 지금 모두 "사람이 눈으로 확인"에 기대고 있다. 6차 재발이 바로 그 확인이 빠진 결과였다.
- **방법**: 이미 있는 기동 텔레그램(`KBS ... 기동 (Python 3.13.14)`)에 점검 결과를 붙인다. 예: `✓ Python 3.13 / ✗ ROI 0개(설정 미복원?) / ✓ ffmpeg / ✗ 오디오 장치 열기 실패 / 디스크 여유 120GB`. Python이 3.14면 맨 앞에 ⚠ 경고를 붙인다.
- **주의**: 텔레그램 토큰이 없는 상태(설정 미복원)에서는 이 알림도 못 나가므로, 같은 내용을 UI 로그창 첫 줄에도 띄운다.

### P3. 하루 1회 생존 보고

- **문제**: 알림이 안 오는 게 "아무 일 없음"인지 "알림 장치 고장"인지 구분할 수 없다(Watchdog 사망, 토큰 만료, 네트워크 차단).
- **방법**: Watchdog이 하루 한 번 정해진 시각에 한 줄을 보낸다. 예: `정상 가동 중 — 가동 3일 4시간, 오늘 알람 2건, 재spawn 0회, Python 3.13.14`. 이 메시지가 안 오면 그 자체가 이상 신호다.
- **관계**: `docs_리포트_구상.md`의 일간 리포트보다 훨씬 작은 선행 단계다. 숫자 몇 개만 세면 되고 이벤트 구조화 저장이 필요 없다. 나중에 리포트가 생기면 이 메시지를 대체하면 된다.

### P4. 디스크 여유 감시

- **문제**: 녹화는 보관 일수(30일)로만 지운다(F7). 알람이 몰리면 디스크가 차고, 녹화와 로그와 heartbeat 쓰기가 같이 실패할 수 있다(추정).
- **방법**: 기존 10분 HEALTH 주기에 `shutil.disk_usage`를 더한다. 여유 공간이 기준(예: 10GB) 아래로 내려가면 `[SYSTEM]` 텔레그램 1회를 보내고, 녹화의 가장 오래된 파일부터 지운다(지우는 건 선택).

### P5. 3.13 테스트 실행 배치

- **문제**: 오늘 이 PC의 `.venv313`에 손으로 `pytest`를 깔았다. 다른 PC나 새 clone에서는 다시 3.14로 테스트하게 된다(F3).
- **방법**: `requirements-dev.txt`(`pytest` 한 줄)와 `테스트실행.bat`(`.venv313\Scripts\python -m pytest`)을 둔다. `.venv313`이 없으면 실행하지 않고 안내한다.

### 제안하지 않은 것

- 새 감지 종류(예: 화면 깨짐, 색 이상): 지금 약점은 감지 능력이 아니라 감시 체계의 맹점이라 우선순위가 낮다.
- AI 해석·일간 리포트: 이미 백로그 문서가 있고 보류 상태라 다시 제안하지 않는다.
