# 타 총국 배포 시 크래시 리포트 구성 — Sentry 적용 여부 최종 판단 대기

생성: 2026-08-31 14:37

## 배경

오늘 세션에서 두 가지를 다뤘다.

1. **8/31 11:46 전체 재부팅 사고 원인 규명** — 같은 PC의 다른 프로젝트 Claude 세션이 `taskkill /F /IM python.exe /T`(이름 기준, PID 미지정)를 실행해 KBS의 watchdog·detection·main이 전부 죽었고, `실행.bat`의 자동 재시작 루프가 살려냈다. 다만 그 루프는 원래 예약재시작 종료코드(42) 전용 설계인데 일반 강제종료로도 돌았다 — "실행.bat를 돌리는 cmd.exe(PID 17544)가 8/12 09:49에 뜬 지 13분 뒤(10:02) 같은 파일이 커밋 `0d53c0f`로 수정됐고, batch의 `goto`는 바이트 위치 기준으로 재탐색하므로 파일이 도중에 바뀌면 어긋난 위치를 읽을 수 있다"는 가설을 세움(정황증거, 미확정). CLAUDE.md에 기록 + 커밋(`64f97c2`) 완료. 실제로 낡은 launcher를 PID 스코프로 정리하고 `실행.bat`를 새로 재기동해 v2.8.11로 정상 기동 확인까지 끝냄.

2. **타 총국 배포 시 크래시 리포트 구성 검토** (이 핸드오프의 본론) — "타 총국에 이 프로그램 배포 시 내가 발견하지 못한 에러를 리포팅 받을 수 있는 크래시 리포트 같은 구성을 만들면 어떨까?"라는 탐색적 질문을 받고 검토함.

## 검토 결과 (결론이 중간에 뒤집힘 — 이유가 중요)

- **1차 추천**: 기존 텔레그램 파이프라인(`system_chat_id`) 재사용. 이유: 이미 각 사이트에서 텔레그램 아웃바운드가 검증돼 있고, Sentry 같은 새 SaaS는 방송국 네트워크에 새 도메인 아웃바운드 허가가 필요할 수 있어 리스크로 봄.
- **사용자가 준 새 정보로 결론 뒤집음**: (a) 배포 방식이 "GitHub에서 그냥 받아가라"는 self-serve 방식이라 총국 10곳이 각자 손으로 설정하는 걸 원치 않음. (b) 다른 프로젝트에서 이미 Sentry를 크래시리포트용으로 쓰고 있음.
- **최종 추천(2차)**: **Sentry**. 텔레그램 봇 토큰은 소스코드에 그대로 박아넣기엔 안전하지 않은 키(노출되면 봇 전체를 남이 장악)라 self-serve 배포와 안 맞는다. Sentry DSN은 "노출돼도 안전"하게(쓰기 전용, revoke 가능) 설계된 키라서 GitHub에 커밋된 소스에 그대로 박아둬도 되고, 그러면 총국 10곳이 각자 아무 설정 없이 `git clone` 즉시 크래시가 개발자(사용자)의 Sentry 프로젝트로 자동 집계된다.

## 사용자 결정 — 지금은 보류

> "일단 handoff만 구성해줘. 다른 프로젝트에서 좀 써보고 최종 판단할께."

즉 **이 프로젝트(KBS_Monitoring_v2)에는 아직 코드를 전혀 건드리지 않았다.** 순수 논의만 하고 끝난 턴이다. 사용자가 다른 프로젝트에서 Sentry를 실제로 운용해보고, 그 경험을 바탕으로 이 프로젝트 적용 여부를 최종 확정할 예정.

## 다음 세션에서 할 일

**전역 CLAUDE.md 규칙 12(계획/검토 요청엔 실행 안 함)에 따라, 사용자가 "이제 (KBS에도) 적용하자"고 명시적으로 말하기 전까지는 아래를 먼저 진행하지 말 것.** 사용자가 확정하면 아래 순서로:

1. `sentry-sdk` 패키지를 `CLAUDE.md`의 "설치된 외부 패키지" 목록에 추가 + 설치 스크립트(`install.bat`/`python313_전환.bat` 등)에 반영.
2. **이 프로젝트가 multiprocessing 3-프로세스 구조(main.py / watchdog_process.py / detection_process.py)라는 점이 핵심 제약** — Windows `spawn` 방식이라 자식 프로세스가 부모의 Sentry 초기화를 안 물려받는다. 세 진입부 각각에 `sentry_sdk.init(dsn=..., release=f"v{VERSION}")`를 따로 넣어야 한다(하나만 넣으면 나머지 두 프로세스의 크래시는 안 잡힘).
3. `before_send` 훅으로 감지 화면 캡처/프레임 데이터 등 민감정보가 리포트에 실수로 안 실리도록 스크럽할 것 — 이 앱은 방송 미공개 화면을 다루므로 이미지 첨부가 크래시 리포트에 섞이면 안 됨.
4. 총국 네트워크가 Sentry ingest 도메인(`*.ingest.sentry.io` 등) 아웃바운드를 허용하는지는 이 세션에서 확인 못 함(총국이 아직 배포 전) — 실제 배포 전 각 총국 네트워크팀 확인이 필요하다는 점을 사용자에게 다시 상기시킬 것.
5. 완료되면 `CLAUDE.md`에 이 아키텍처 결정(왜 텔레그램이 아니라 Sentry인지 포함)을 문서화.

## 판단 기준 (다음 세션이 헷갈릴 만한 지점)

- 왜 텔레그램이 아니라 Sentry인가 다시 물으면: "총국들이 각자 봇 설정을 안 해도 되는 self-serve 배포"가 결정적 이유였다 — 단순히 "Sentry가 더 좋아서"가 아니라 이 프로젝트의 배포 방식(GitHub clone)과 사용자가 이미 보유한 도구(Sentry 계정)가 맞아떨어져서 나온 결론이다. 배포 방식이 바뀌면(예: 담당자가 직접 설치해주는 방식으로 회귀) 재검토 여지 있음.
