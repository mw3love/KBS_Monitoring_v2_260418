# 녹화 오디오 수정 실조건 확인 + "소리 점점 커짐" 재검토

생성: 2026-09-22 08:50

## 배경

사용자 보고: 자동 녹화 MP4가 **ⓐ 처음에 소리가 안 나고 ⓑ 점점 소리가 커진다**.

2026-09-22 세션에서 ⓐ만 원인 특정·수정 완료. ⓑ는 **재현 실패로 보류** — 사용자가
"지금 파일 보면 소리가 커지는 것 같지는 않다, 나중에 해당 파일 얻으면 다시 말하겠다"고
답해 일단 덮어둔 상태.

## ⓐ 수정 내용 (커밋 `6a86af2` + 문서 `c650538`)

`detection/auto_recorder.py` 한 파일.

원인(재현으로 확정): 영상 pre버퍼는 **프레임 개수**(`pre_seconds × out_fps` = 105장),
오디오 pre버퍼는 **샘플 수**(440청크 = 10.2초)로 크기가 정해져 덮는 시간이 달랐다.
`push_frame`의 실효 fps가 선언값 10이 아니라 **9.33fps**(캡처 루프 33ms + 0.1초 게이트의
양자화)라 영상 버퍼가 11.1초를 덮었고, 그 차이(1~3초)를 `ffmpeg -itsoffset`이 무음으로
메워 파일 머리가 통째로 무음이었다.

조치 3가지:
1. pre버퍼 두 개의 시작점을 늦은 쪽에 맞춰 트리밍 (무음 유입 경로 차단)
2. 프레임 타임스탬프로 실효 fps 산출 → `-itsscale`로 재생 속도 보정 (재인코딩 없음)
3. A/V 정렬 계측을 `_log.info` → `LogEntry`로 변경
   (`auto_recorder._log`는 핸들러가 없어 **어느 로그에도 안 찍히고 있었음**)

하네스 재현 검증(이 PC, 실오디오 장치): 오디오 start_time 1.012s → **0.000s**,
영상 19.80s/실제21.1s → 20.06s/실제20.1s, 잔여 어긋남 70ms/20초.

Detection 프로세스는 2026-09-22 08:49 재기동(PID 17784)해 **새 코드로 돌고 있음**.

## 다음 세션에서 할 것

### 1. 실조건 확인 (다음 실제 알람 녹화본으로)

`recordings/`에 2026-09-22 08:49 이후 생성된 파일이 있으면:

```bash
ffprobe -hide_banner -show_streams <파일> 2>/dev/null | grep -E "^codec_name|^start_time|^duration=|^nb_frames|^r_frame_rate"
```

판정 기준:
- 오디오 `start_time` ≈ **0.000** (이전 실측값: 8/28 파일 2.922) → ⓐ 해결
- 비디오 `r_frame_rate`가 10/1이 아니라 **실측 실효값**(예: 28/3) → 보정 발화함
- UI 로그(`logs/YYYYMMDD_ui.txt`)에 `[recorder] 녹화 A/V 정렬: ...` 줄 존재 → 계측 복구 확인

이게 확인돼야 상태가 **프록시검증 → 실조건검증**으로 올라간다.
(주의: 그 줄은 `level="debug"`라 로그창에서 "개발자" 토글을 켜야 화면에 보인다. 파일엔 남는다.)

### 2. "점점 소리가 커짐"(ⓑ) 재검토 — 사용자가 파일을 줄 때만

이미 배제된 것(다시 하지 말 것):
- `20260828_150547_276_V5_2TV ON-AIR_black.mp4` 초당 RMS 실측 = 634/841/763/365/410/687…
  → **램프 없음(평탄)**. 이 파일엔 증상이 없다.
- 증폭 코드 경로 없음: `audio_monitor.py`의 volume 스케일링은 **패스스루 출력 전용**이고
  녹화로 가는 `on_audio_chunk`은 원본 int16 그대로다.

남은 가설(미검증):
- 다른 파일에만 있는 현상 → 파일 확보가 선결
- 사용자가 **싱크 어긋남**(수정 전 영상 6.5% 빠름)을 그렇게 표현했을 가능성 →
  이 경우 이미 수정됨. 1번 실조건 확인이 곧 반증 실험이 된다.
